# A01 — claude-code

> The reference adapter. Its SDK maps almost one-to-one onto the unified contract, and it is the only adapter that can both *define* subagents and *push* a message mid-turn — so it is the yardstick every other adapter degrades against.

<!-- anchor: 4o8v4n21 -->
## Purpose & SDK identity

Wraps `@anthropic-ai/claude-agent-sdk` (optional peer dependency — imported lazily inside `execute()` so loading the package never hard-requires the SDK). It is the closest mapping to `UnifiedEvent` and the implementation other adapters are measured against. Architecture id `claude-code`, with provider variants `claude-code-ollama` and `claude-code-minimax` (see M03).

<!-- anchor: mn3ytsj4 -->
## Event mapping (L1)

How each SDK message becomes a `UnifiedEvent`:

| SDK message | UnifiedEvent |
| --- | --- |
| `stream_event` → `content_block_delta` → `text_delta` | `text_delta` |
| `stream_event` → `content_block_delta` → `thinking_delta` | `thinking` |
| `assistant` | `assistant_message` (+ `tool_use`, `todo_list_updated`) |
| `user` (tool_result blocks) | `tool_result` |
| `tool_use_summary` | `tool_result` |
| `system` `task_started` / `task_progress` / `task_notification`, `task_type` = subagent | `subagent_started` / `subagent_progress` / `subagent_completed` |
| `system` `task_started` / `task_progress` / `task_notification`, `task_type` ∈ `'shell'` / `'monitor'` / `'workflow'` | `background_task_started` / `background_task_progress` / `background_task_completed` (M17) |
| `system` `compact_boundary` | `flush` |
| `result` (`subtype: success`) | `result` |
| `result` (non-success) | `error` (runtime phase) |
| `AskUserQuestion` via `canUseTool` / `onElicitation` | `user_input_request` (+ legacy `elicitation_request`) |
| accepted `pushMessage` | `user_message` |

The SDK multiplexes real subagents **and** backgrounded side work onto one `task_*` channel; `SDKTaskStartedMessage.task_type?` (plus `subagent_type?` / `workflow_name?`) is the discriminator. Because `task_progress` / `task_notification` carry only `task_id` / `status` / `output_file` / `summary` / `usage` (no `task_type`), the adapter must capture `task_type` on `task_started` into a `Map<task_id, task_type>` and route every later message for that `task_id` through it — subagent kinds to `subagent_*` (M06), `'shell'` / `'monitor'` / `'workflow'` to `background_task_*` (M17). Those three are the **unified** kinds (M17's vocabulary), not the literal wire strings — the live SDK values are `local_`-prefixed (e.g. `local_bash`) and stripped before this routing, per the `task_type` spellings note below. Unknown / absent `task_type` defaults to the subagent path (legacy behavior). A second `task_started` for a `task_id` already in the map **refreshes** the entry rather than being ignored: a re-entered subagent (M06) re-uses its `task_id`, so the map has to survive a second cycle, and a `task_type` that changed between cycles is a schema-drift signal, not a routing decision to smooth over. `subagentTaskId` is resolved through a `parent_tool_use_id` → `task_id` map written on **every** `task_started` that carries a `tool_use_id`, so a re-entry **adds a second key** pointing at the same task rather than replacing the first. The extra key is harmless and is deliberately not suppressed: the resumed agent's assistant messages keep carrying the **original** `Agent` tool_use id, so the original entry is what resolves `subagentTaskId` and the new key is never read. Attribution therefore survives re-entry with no special handling — which is the guarantee M06's `resumed` marker leans on. Task-tracking `tool_use` blocks project to `todo_list_updated` (source `model-tool`) with their echoed `tool_result` suppressed as redundant; the `TodoWrite` ↔ `TaskCreate/…` matrix, the `ToolSearch` gate, snapshot accumulation, and the rename-durable projection semantics are owned by M16 (see <section_ref anchor="3dln3isl"/>).

The harness **scheduling** family (`ScheduleWakeup`, `CronCreate` / `CronList` / `CronDelete`, and the `/loop` slash command) has **no row above**: these tools are hard-suppressed before they can reach the stream, so they never map onto any `UnifiedEvent` (see <section_ref anchor="sw3cwrsm"/>). `Monitor` is *not* in this family — it works headless (it streams a background process) and stays an ordinary `tool_use` → `assistant_message`.

## Capability support & degradation (L2)

This adapter is the positive column in every capability matrix — those matrices live in the capability-modules (one-home rule), not here:

- MCP transports → M04 owns the matrix; claude-code accepts all four (stdio, SSE, HTTP, in-process SDK).
- Subagent definition → M06; claude-code is the only adapter where `subagentDefinition` is true.
- Mid-turn push → M11; claude-code is the only adapter where `midTurnPush` is true.
- Images → M10; accepts base64 + url, materializing `file` sources to inline base64.
- Path-scope → M15 owns the matrix; claude-code is the only adapter with a fine-grained, **deny-expressible** gate and is **hard-capable** (OS sandbox) — soft by default, hard on opt-in.
- Background tasks → M17 owns the matrix; claude-code is today the only adapter with engine-backgrounded shell work (`run_in_background`) and SDK-native session-hold on in-flight tasks.

`architectureCapabilities('claude-code')` returns `{ midTurnPush: true, imageInput: true, subagentDefinition: true, pathScope: true, toolGating: true }`.

Agent-team and cross-session peer messaging are **not** declared capabilities in either direction: no `architectureCapabilities` flag covers them, and no degradation applies, because no other adapter has an equivalent to degrade from.

## Per-capability consumption

- **Models** (<section_ref anchor="9gu9zp7z"/>) — `resolveModel('claude-code', …)`; honors `claude_thinking` (auto-converts `enabled` → `adaptive` for `ADAPTIVE_THINKING_ONLY` models) and restores the `summarized` thinking display for Opus 4.7.
- **MCP (M04)** — passes the unified `mcpServers` config straight through; in-process `sdk` servers are handed over by instance.
- **Skills (M05)** — materializes `InlineSkill`s into a per-call tmpdir registered as a `local` plugin; the `Skill` tool stays available under a `file-write` deny (so the plan-mode preset keeps skills), and is suppressed under a `shell` deny, because a skill can drive the shell (M05 — <section_ref anchor="6rir81wb"/>).
- **Subagents (M06)** — maps `subagents` to `Options.agents`; both defines and observes lifecycle. The envelope's fields and its inheritance rules are M06's (<section_ref anchor="6fh6yq89"/>); what belongs here is the wiring.
  - `name` becomes the **key** of `Options.agents` — the SDK's `AgentDefinition` has no name field of its own.
  - `tools` / `disallowedTools` pass through `subagentToolPolicy`, the M18 intersection M06's propagation rule requires. Stated exactly, because the two cases differ: when a tool policy is in play the subagent's `tools` is **always pinned** — to the filtered list, or to the run's full residual allow-list where the definition omitted the field; when there is no policy neither field is sent at all and the SDK's own inheritance applies.
  - `model`, `skills`, `maxTurns`, `effort` map 1:1, and an unset field is omitted from the SDK object entirely rather than sent as an explicit null, so the SDK default applies.
  - *Re-entry (`SendMessage`).* The `Agent` tool result instructs the model to continue a backgrounded helper with `SendMessage`, and the SDK backgrounds `Agent` by default at this pin (`AgentInput.run_in_background` — *"Agents run in the background by default"*; `AgentInput.name` — *"Makes it addressable via `SendMessage({to: name})` while running"*), so re-entry is the ordinary path, not an exotic one. The model reaches `SendMessage` through the `ToolSearch` discovery gate — no published SDK catalog lists it. Measured at 0.3.263: the tool result is `{ success: true, message: 'Resuming agent <short>', resumedAgentId: <task_id>, pin: { id, name, ref } }`; the SDK then emits a **new** `system` `task_started` with the **same** `task_id`, `tool_use_id` = the `SendMessage` tool-use id, `is_backgrounded: true` (`SDKTaskStartedMessage.is_backgrounded` — *"A resumed subagent is always registered in the background"*) and `prompt` = the new message; a second `task_updated` (`completed`) and `task_notification` follow, and the session is held open until it reports (M17 — <section_ref anchor="01or0cpk"/>). The resumed agent's assistant messages keep `parent_tool_use_id` = the **original** `Agent` tool-use id, so attribution is unchanged (see <section_ref anchor="mn3ytsj4"/>). `task_started` carries **no** `resumed` field, so the marker is adapter-derived from "this `task_id` has been seen before", and the adapter maps the re-entry to a second lifecycle pair with `resumed: true` (M06 — <section_ref anchor="0f6287ae"/>).
- **Images (M10)** — builds Anthropic image blocks; a `file` image is read and inlined as base64.
- **Mid-turn (M11)** — runs a real streaming-input channel (`AsyncIterable<SDKUserMessage>`); `pushMessage` enqueues and the channel stays open across turns while messages are pending. The channel backs **every** run, `streamingInput` or not (reason in the M17 bullet below); only `pushMessage` is gated on the flag.
- **Abort / timeout (M13)** — `abort()` must break the loop wherever it can park, including an `await` on the consumer's `onUserInput` handler, which a UI-backed consumer may never resolve. Teardown is: fire the abort signal (breaks every awaited point, including the raced `onUserInput`), answer the outstanding request `cancel` (so the SDK-side promise settles instead of leaking), and close the input channel — after which the run yields `AdapterAbortError` / `AdapterTimeoutError` and no SDK subprocess is left dangling. This M13 guarantee is **behavioural**: it does **not** depend on cooperatively interrupting the engine. `Query.interrupt()` is available on every run now that the channel path is universal, but it is a control-protocol round-trip over the *same* stdin that teardown then closes, so **it must never be awaited on the teardown path** — awaiting it can outlive its transport and never settle, reintroducing exactly the parked-run failure M13 exists to prevent. If the adapter calls it at all it is strictly **fire-and-forget**; a rejecting, synchronously-throwing, or entirely absent `interrupt()` still terminates the run.
- **Resume (M07)** — sets `options.resume`; usage reported by `result` covers this `query()` only, **not** the resumed session's history.
- **Path-scope (M15)** — realizes M15's **allow-confinement** contract, not a bare deny-list.
  - *Soft default.* When path-scope is requested the run switches **off** the adapter's usual `permissionMode: 'bypassPermissions'` (under which everything not explicitly denied is auto-approved — allow-confinement is impossible) and onto a **default-deny** mode (`permissionMode: 'default'`/`'dontAsk'`) with `permissions.allow` rules for `cwd ∪ allowedPaths` and `permissions.deny: ['Read(…)','Edit(…)']` rules for `disallowedPaths`. This confines reads/writes to the ceiling (model-visible). Outside path-scope the adapter keeps today's `bypassPermissions`, so consumers not using scope see no regression.
  - *Hard gate (opt-in).* Enabling `claude_sandbox.enabled` enforces at the OS syscall level (bubblewrap/seatbelt): `sandbox.filesystem` `allowWrite`/`denyWrite`/`denyRead` for write confinement, plus **managed allow-read confinement** (`allowManagedReadPathsOnly` + `allowRead` for `cwd ∪ allowedPaths`) for reads — because the SDK's default read model is deny-based, merely allowing the scope would not exclude the rest. When the OS sandbox is requested but unavailable on the host, the gate degrades hard→soft with a `warning`; a security consumer reads the runtime strength signal before dispatch (the static capability only says *hard-capable*).
  - *Config-discovery containment.* When path-scope (or the sandbox) is requested the adapter narrows `options.settingSources` to exclude the global user tier (`~/.claude`), disabling ambient global settings and disk-skill discovery that could otherwise re-widen the agent's reach outside scope. Inline skills are delivered via `options.plugins` (see M05), so this narrowing does **not** disable inline-skill materialization.
- **Usage (M08)** — rolls Anthropic's three input buckets (`input` + `cache_read` + `cache_creation`) into a single `inputTokens`; `contextSize` = input + output. Each `result` reports **that turn's own cost**, so no delta subtraction is needed (unlike codex): measured across both pins, a run's second `result` routinely reports fewer tokens than its first in every field, which a running total cannot do. A run that emits several `result`s — a mid-turn push (M11) or a background-work wake-up (M17) — is billed as their sum.
- **Tool gating (M18)** — realizes deny-groups as a **residual allow-list** on `options.tools`, with `disallowedTools` as the backstop that also strips the tool from model context; the group→identifier mapping and the strength this earns are canon in M18 (<section_ref anchor="1yllld10"/>). Three adapter-side rules the module points here for:
  - *Never the settings permission surface.* An M18 deny rides `tools` and `disallowedTools` only. `permissions.allow` is the channel M15's default-deny path-scope and `autoApproveTools` both write to, so a deny expressed there sits on a surface those can re-widen; `disallowedTools` cannot be widened and removes the tool before the model sees it. Moving a group onto `permissions.deny` would trade that property away for nothing.
  - *Durability of the allow-list.* It must track *every current alias* of a renamed or relocated built-in across SDK versions — the discipline already applied to `Task` → `Agent` — and must keep nine built-ins — `TodoWrite`, `TaskCreate`, `TaskGet`, `TaskUpdate`, `TaskList`, `ToolSearch`, `AskUserQuestion`, `Task` and `Agent` — available **unconditionally under any deny**, not merely when writes are denied (the task-tracking family, its `TodoWrite` ↔ `TaskCreate/…` drift and projection semantics owned by M16 — <section_ref anchor="3dln3isl"/>). So a plan-mode turn on a newer model always retains a usable task-tracking tool and never degrades to prose-only planning, a run can always put a question to its consumer, and a deny on one group never costs the run its ability to delegate or to continue a helper it already spawned. An invariant on behavior, not on a frozen tool list. The `shell` group is where that discipline has gone stale: it names `Bash`, `BashOutput`, `KillBash` and `KillShell`, of which the SDK canonicalises the last three to `TaskOutput` and `TaskStop` — and neither canonical spelling appears anywhere in the adapter, so the task inspector is denied under its retired name and exempt under its current one. Both canonical names belong in the `shell` group beside the legacy ones, and the alias map the SDK ships is the authority for what *every current alias* means at a given pin: an alias inventory kept from memory is how a gate silently stops firing.
  - *The allow-list must carry the delegation family, and the inventory must be complete.* The adapter builds `options.tools` — the SDK's **base set of available built-in tools**, a replacement rather than a filter — from a hand-kept inventory whenever any deny-group is set, so omission from that inventory is removal. At this pin the inventory names 24 built-ins against a published catalog of 45, so 29 catalogued tools are stripped by a deny that has nothing to do with them, `TaskOutput` and `TaskStop` among them. `SendMessage` and `ListAgents` (current alias `ListPeers`) are worse than merely missing: they appear in **no** published SDK list at all — the model reaches them through the discovery gate — so an inventory derived from what the SDK advertises would still omit them. Measured at 0.3.263, a gated run reports `SendMessage: false, ListAgents: false` at `system:init` and then tells the model the tool does not exist. The rule is M18's general one (<section_ref anchor="4j6f86yq"/>); the adapter-side obligation is that the inventory is maintained by hand, audited on every pin bump, and names every alias the SDK canonicalises.
  - *Why not `permissionMode: 'plan'`.* The SDK's own plan mode would make the model defer consumer-curated MCP tools too, which M18 explicitly does not gate (M04 — <section_ref anchor="fv7bhx0s"/>).
- **Background tasks (M17)** — the Bash tool's `run_in_background` parameter backgrounds the shell process (never the agent). Mechanics the adapter realizes:
  - *`task_type` capture & routing.* Read `task_type` (+ `subagent_type?` / `workflow_name?`) on `task_started`, keep the `Map<task_id, task_type>`, and route `task_progress` / `task_notification` (fields: `task_id`, `status`, `output_file`, `summary?`, `usage?`) to `background_task_*` vs `subagent_*` accordingly (see the mapping table above). Absent or unrecognized `task_type` keeps the subagent path, so an SDK that stops sending the discriminator degrades to the pre-M17 shape rather than misrouting.
  - *In-flight tracking is adapter-side.* `SDKResultMessage` carries no in-flight list (the SDK exposes `background_tasks[]` on `StopHookInput` / `SubagentStopHookInput`, not on `result`), so the adapter maintains the set itself. **Both** kinds are tracked, because both can outlive the turn's `result` — a late-settling subagent is the shape the original bug report showed. Two signals move a task through the set: `task_updated` carrying a terminal `patch.status` marks it *finished* — which is what distinguishes "still working" from "done, wake-up pending", and so which hold bound applies — and `task_notification` removes it and emits the completion event. Measured on 0.3.153 and 0.3.210: `task_updated` precedes its `task_notification` by milliseconds, and both fire for subagents as well as for backgrounded shell work.
  - *Holding is not reporting.* The tracked set drives the **hold** for both kinds — a subagent holds the session exactly as a backgrounded command does — but it populates M01's `result.backgroundTasks` for **background kinds only**. Listing a subagent there would promise a `background_task_completed` that never arrives, and M17/M01 define the field as never-a-subagent. An engine-supplied list — `StopHookInput.background_tasks` today, a `result.background_tasks` field should a future SDK add one — is unioned with the tracked set, never substituted for it, and every entry is classified through the same `task_type` mapping first: `BackgroundTaskSummary.type` is a **display label**, and on 0.3.210 it is literally `'subagent'` for helper agents, so passing it through unclassified both leaks subagents into the signal and mislabels `local_bash`.
  - *`task_type` spellings are observed, not assumed.* Live against 0.3.153 a `run_in_background` Bash command reports `task_type: 'local_bash'` — not `'shell'`; the SDK prefixes locally-executed kinds with `local_` (`local_workflow` appears alongside `workflow_name`). The adapter strips that prefix before mapping. The type declarations say only `task_type?: string`, so any table of kinds must be checked against a live probe, never inferred from the types.
  - *Push resume — the run ends at iterator `done`, and the **input channel** must outlive `result`.* The SDK holds the `query()` open while background work is in flight: the turn's `result` arrives, the session pauses, and on `task_notification` the SDK wakes the model, which continues to a further `result`. Ending the adapter's consume loop only on `done` is necessary but **not sufficient** — the CLI is spawned with `--permission-prompt-tool stdio`, so its permission/control protocol shares the prompt channel (stdin). Closing that channel at `result` leaves the loop running over a session whose control transport is dead: the woken model's `AskUserQuestion` is denied inside the CLI within milliseconds, with no host round-trip and no error on the stream. The adapter therefore keeps the channel open while its tracked set is non-empty (M17's control-channel hold), and closes on the continuation `result` once the set has drained.
  - *One-shot runs use the channel too.* A plain string prompt makes the SDK mark the query single-turn and call `transport.endInput()` on the first `result` — the same stdin close, done by the SDK where the adapter cannot intervene. So **every** run is driven through the seeded input channel; `streamingInput` continues to gate `pushMessage()` only (M11 — <section_ref anchor="fr2hhuye"/>). This also makes the streaming-only control surface (`Query.interrupt()`) *available* on ordinary runs — availability, not a requirement: adapter teardown does not depend on it (see the Abort/timeout bullet above). Empirically the string-prompt path additionally loses the post-`result` wake-up outright on some peer-range SDK versions, which the channel path does not.
  - *Whether to hold: the `Stop` hook answers half the question.* `StopHookInput.background_tasks` is documented as letting hooks "distinguish 'session is done' from 'session is paused waiting for background work to wake it'", and the adapter registers a `Stop` hook (additively, alongside the disable-lever `PreToolUse` hook and project hooks from `settingSources`) to read it. **Measured, both pins:** it fires ~3ms *before* the `result` it belongs to, and its positive answer is exact. Its *empty* answer is not — on 0.3.153 the three-subagent shape reported `[]`, after which the engine held the session, woke the model 2ms later, and ran a further full turn; 0.3.210 does list subagents there (`type: 'subagent'`), so the gap is version-dependent across the supported range. It is therefore consumed as a **positive hold reason only**, unioned with the adapter's own tracking, and never as permission to close.
  - *The hold is bounded, and neither bound may fire while the model is producing.* A **grace window** armed only once everything tracked has settled and re-armed by every frame that arrives while parked (so it measures engine silence — the engine really does emit `system/status` and `system/background_tasks_changed` frames while it babysits work, and the previous version let any one of them disarm the grace outright); and an absolute **cap** on the parked stretch, released the instant a continuation turn's first main-model frame arrives, because from there the run is an ordinary live turn bounded by `timeoutMs` / `abort()` (M13). Subagent chatter (`parent_tool_use_id` set) is not a resumption and does not release it. **The two bounds end the run differently, and that asymmetry is the whole point:** grace closes the input channel and lets the run finish silently at its `result`, exactly where the pre-hold adapter closed it; cap **interrupts and aborts the session** — down the same teardown path `abort()` uses — so the loop surfaces a terminal `AdapterBackgroundHoldExpiredError` (M13 — <section_ref anchor="8q9q7ty7"/>) naming the cap and the lever, and nothing follows it. Closing the channel on cap expiry instead is the defect this release fixed: the CLI is still alive at that moment, stdin is its only host→CLI control transport, and the session carried on with MCP, `canUseTool`, hooks and elicitation all silently dead while the consumer saw nothing but `(<tool> completed with no output)` results. The adapter emits **no** `warning` about the hold on any path (M17 — <section_ref anchor="q9u5sbot"/>).
  - *Grace sizing is an empirical result, not a preference.* What it must cover is the gap between the last task settling and the first frame of the continuation turn. Measured with `includePartialMessages` (which the adapter always sets): **3.5s** (backgrounded bash) and **3.7s** (three subagents) on 0.3.210; **5.0s** on 0.3.153 without partials. A 5s window therefore had no margin at all, and expiry mid-wake-up closes the control transport — the defect this whole section exists to prevent. The constant is set well above the worst observed (**15s**, ~4× the worst) and re-measured whenever the peer range moves.
  - *Both bounds are levers, and the cap has a ceiling it must respect.* `architectureConfig.claude_backgroundGraceMs` / `claude_backgroundHoldCapMs` (L3 keys, contract in M17) let a consumer trade the tail against the risk of cutting a wake-up short — the grace is dead time paid at the end of **every** run that started any task, including one whose subagents all finished in-turn, and only a consumer knows its own wall-clock budget. A non-numeric or non-positive value degrades to the default rather than disarming the bound. The cap default is **90s**, deliberately under the 120s default of the library's own `collectEvents()` helper: that clock starts earlier (at the run's start, not at the held `result`), so an equal cap could never surface its `AdapterBackgroundHoldExpiredError` — the helper would reject the run first and the abandoned background work would be reported as a plain timeout.
  - *Disable recipe.* There is no SDK option to forbid backgrounding; the lever is a synthesized `PreToolUse` deny-hook that rejects any Bash call with `run_in_background: true` (forcing synchronous execution). Proposed config surface: `architectureConfig.claude_disallowBackgroundBash: true` (L3 key, default off) — contract in M17.
  - *Known gaps (unused SDK controls).* `Query.stopTask()`, `Query.backgroundTasks()`, and the `is_backgrounded` flag are not consumed — per-task stop and mid-run enumeration are unrealized; `abort()` remains the coarse stop (M13). (`StopHookInput.background_tasks` *is* consumed — see the hold bullets above.)
- **Cross-session ingress (out of scope — pinned, not ignored)** — the same `SendMessage` tool also addresses agent-team teammates and peer agents in other sessions (local, Remote Control, cloud). `crossSessionInbound` (`'accept' | 'hold' | 'refuse'`) governs turns arriving **inbound**, and it is a **`Settings`** key, not a query option. Left unset it follows **mode parity** — *"a message auto-delivers only when the sending session's permission-mode class matches yours (bypass↔bypass or prompting↔prompting)"* — so a `bypassPermissions` library run auto-accepts inbound turns from any other bypass session on the machine: unauthenticated ingress into a consumer's process through a default they never chose. The adapter therefore pins `crossSessionInbound: 'refuse'` on **every** run via `options.settings`, merged into the object the soft path-scope branch already writes there (Path-scope bullet above) and set whether or not path-scope was requested. **Not** via `managedSettings`, which is filtered restrictive-only and drops a non-allowlisted key silently, so the pin could vanish with no error. The pinned value is reported in the `adapter_ready` `sdkConfig` (M14 — <section_ref anchor="0tycjmv6"/>); `isolatePeerMachines` is left at the SDK default. There is no config key to re-open it: a library embedded in someone else's process is not the layer that decides to accept traffic from another session (<index> open question 9).
- **Outbound peer messaging — gated, not merely unspecified** — a `query()` run registers as an **addressable peer session**: `ListAgents` returns this run's own peer name plus every other session of the same user, by name, short id, kind and state, and `SendMessage({to})` can inject a prompt into any of them. An embedded library must not be able to drive its host's interactive sessions, and no SDK option turns sending off on its own — `isolatePeerMachines` only requires approval for reaching a peer on **another** machine. Because the same tool also re-enters this run's own subagents, the gate cannot be the tool list, and it cannot be a `delegation` deny either: both close re-entry too. It is an input predicate on `canUseTool` — a `SendMessage` whose `to` resolves to a task this run started is allowed, any other `to` is denied with a message saying so. `ListAgents` stays allowed, but its listing is the consumer's session inventory, which the run has no business carrying (M14 — <section_ref anchor="0tycjmv6"/>).
  - *The hook becomes unconditional.* `canUseTool` is installed today only when the consumer supplies a user-input handler, and it currently allows everything except `AskUserQuestion`. The outbound gate changes **when** the hook exists as well as what it decides — a run that previously sent the SDK no `canUseTool` now sends one — and that is a behaviour change worth stating rather than discovering.
  - *The predicate needs no new bookkeeping.* "A task this run started" is already decidable from the adapter's own task registry: every `task_id` is recorded at `task_started` and no entry is ever removed, so the same state that drives the background hold (Background tasks bullet below) also answers the `to` predicate.
  - *Semver — this narrows, it does not add.* The gate removes something a run could previously do, so it is not an additive change: a consumer relying on outbound peer messaging would break, though there is none today because the contract never advertised it. It is classified exactly as the `crossSessionInbound` pin is — a security default, reported in the `adapter_ready` `sdkConfig` so a posture the consumer did not choose is at least one they can observe (M14 — <section_ref anchor="0tycjmv6"/>) — and M12 carries the release classification.
  - *The listing leak is documented, not closed.* `ListAgents` is deliberately **not** denied: the model needs it to discover the helpers it spawned, nothing in the adapter reads its result, and no unified event is derived from it. It does carry the names of the consumer's unrelated sessions into the model's context, and that exposure is recorded as a known one rather than mitigated. The reason, kept here so the next round does not re-litigate it: listing is not reaching. The control that matters sits on the reaching tool, and it is the `to` predicate above; denying the listing would have looked like a mitigation while changing nothing about what the run can actually do.
- **Scheduling (harness) — hard-suppressed** — the harness scheduling subsystem (`ScheduleWakeup`, `CronCreate` / `CronList` / `CronDelete`, `/loop`) is a construct of the *interactive* Claude Code harness, not a primitive of `@anthropic-ai/claude-agent-sdk`. Under the headless drive this library uses, a scheduled wake-up never fires: the model calls the tool, the turn ends, and the requested work is **silently lost** with no error. The adapter therefore hard-suppresses the whole family — always, with no config gate. Mechanism (behavior, not code): set `CLAUDE_CODE_DISABLE_CRON=1` via `custom_env` (kills the scheduler, `/loop`, and the cron tools) and/or append the tool names to `disallowedTools` — the same wiring the tool-gating bullet above uses. This suppression is unconditional and is not an M18 group: no consumer asked for it, and there is no deny-group under which the family would make sense. `Monitor` is deliberately **excluded** from this suppression: it works headless.

## Auth model (L6)

The SDK manages credentials internally — local OAuth / cached subscription credentials or `ANTHROPIC_API_KEY`; **no API key is required** for the subscription OAuth path. Provider variants inject `ANTHROPIC_BASE_URL` (and provider env) through `custom_env` (see M03). Failure mode: an init-phase fault — model resolution, SDK import, skill materialization, or image build — is emitted as an `error` event with `phase: 'init'` (`AdapterInitError`), never thrown.

- **Supported peer-SDK range** — `@anthropic-ai/claude-agent-sdk` `>=0.3.0 <0.4.0` (the 0.3 line verified in CI). The **dev-pin** inside that range is a separate, faster-moving decision: the target is the *latest 0.3.x at brief time, minimum `^0.3.251`* — below that floor the Claude Code CLI bundled in the SDK refuses the newest resolved ids in the M02 catalog, so a lower pin cannot exercise the catalog it is meant to verify (mechanism in the next bullet). - **Bundled-CLI coupling** — the `@anthropic-ai/claude-agent-sdk` tarball ships a Claude Code CLI executable whose version tracks the SDK's patch: `0.3.N` bundles CLI `2.1.N`, verified by unpacking the published 0.3.220, 0.3.251 and 0.3.263 tarballs. The adapter's bridge stays in place for the day the client advertises it; the live e2e for it self-skips with the refusal message rather than pretending to pass.

## Edge cases

- `timeoutMs` exceeded → `AdapterTimeoutError`; `abort()` → `AdapterAbortError`; both runtime-phase, and the input channel is closed.
- background work parked past the hold cap → `AdapterBackgroundHoldExpiredError` (runtime phase), carrying the cap that was hit; the session is interrupted and aborted and the `error` is the run's last event. Distinct from the two above by class and by `name`, because the consumer's reaction differs: the budget was not too small and nobody aborted — the engine's background work stalled and is abandoned unfinished (M13 — <section_ref anchor="8q9q7ty7"/>).
- Under cPanel/Passenger or CageFS, `ensureUsableStdin()` replaces a throwing `process.stdin` **before** the SDK is imported (see M13).
- An M18 deny-group is applied to the parent's tool set, but a spawned subagent does not inherit `disallowedTools` — matching native Claude Code behavior. This is the escape surface M18 names for the `shell` group (<section_ref anchor="1yllld10"/>), and it is why the group reports `soft`: it is closed by propagating the groups into every subagent definition (M06 — <section_ref anchor="0f6287ae"/>), not by the parent's deny alone.
- `file-read` denied while `shell` is allowed → the deny holds for `Read` / `Grep` / `Glob`, but native builds may serve search through the shell, so the group is bypassable and reports `soft` with that escape surface named. The run still proceeds; M18's porous-combination `warning` is what tells the consumer.
- streaming-input run → may emit multiple `result` events; a `pushMessage` arriving after the channel closes returns `false`.
- path-scope with the OS sandbox enabled → a Bash subprocess writing outside scope is blocked at the syscall level (no `command` parsing); under the soft default it is only protected by `Bash(...)` permission patterns. Host without bubblewrap/seatbelt → hard→soft degradation with a `warning`.
- path-scope requested → the soft run drops `bypassPermissions` for a default-deny mode; a read of a file outside `cwd ∪ allowedPaths` is blocked even when it is not named in `disallowedPaths`. Outside path-scope the run keeps `bypassPermissions` unchanged.
- path-scope / sandbox requested → `settingSources` is narrowed to drop the global `~/.claude` tier, so global `settings.json` and disk skills there are not discovered; inline skills (via `options.plugins`) are unaffected.
- `run_in_background` Bash call → the turn's `result` arrives with the background task still running; the SDK holds the session open and the completion (`task_notification` → `background_task_completed`) plus the continuation turn arrive **before** iterator `done`. A consumer that stops at the first `result` never sees them (M17's canonical bug).
- `run_in_background` Bash call → the woken model's `AskUserQuestion` still reaches the consumer, because the input channel outlived the turn's `result`. Closing it there instead produces the failure signature this rule exists to prevent: a `tool_result` reading `Tool permission request failed: … Stream closed`, the model retrying and then asking in prose, and no `user_input_request` on the stream.
- `abort()` while a `user_input_request` is outstanding and the consumer's handler is still pending → the run terminates with `AdapterAbortError` and the SDK subprocess is torn down; it does **not** wait for an answer that may never come.
- harness scheduling tools (`ScheduleWakeup`, `Cron*`, `/loop`) are inert under the headless SDK — they would end the turn without ever firing the wake-up, silently dropping the scheduled work → the adapter **hard-suppresses** them so the model never sees them (no silent no-op). `Monitor` is exempt (it works headless) and stays available.

- The model re-enters a backgrounded subagent with `SendMessage` → a second `subagent_started` for the same `taskId`, marked `resumed: true`, and the run does not end at the intervening `result`: the session is held until the resumed agent reports. A consumer keyed on one lifecycle pair per `taskId` must be prepared for a second.
- A deny-group is set and the model tries to continue its own subagent → it must still be able to. The `options.tools` allow-list the deny triggers carries `SendMessage` and `ListAgents` (with its alias `ListPeers`); without them the model reports that no `SendMessage` tool exists and the delegation it already started is stranded — visible only as prose, never as an error.
- A deny-group is set and the model reaches for any built-in the adapter's inventory does not name → it is blocked, whatever that tool does. `options.tools` replaces the SDK's base tool set rather than filtering it, so the inventory's completeness, not the deny's scope, decides what survives. Same failure as the bullet above, one level up from its first reported instance.
- A `task_started` re-arrives for a `task_id` whose entry was already marked finished → the entry re-enters the in-flight set, both hold bounds re-arm, the finished mark is cleared, and the `task_type` map entry is refreshed rather than kept stale.
- Another local session sends this run an inbound turn → it is refused, because `crossSessionInbound` is pinned to `'refuse'` through `options.settings`. Nothing reaches the model and nothing appears on the unified stream. Left unset the SDK would follow mode parity, and a `bypassPermissions` run would have accepted a turn from any other bypass session on the machine.
- The model calls `SendMessage` with a `to` that is not a task this run started → denied, with a message saying the run may only address its own subagents. The tool itself stays in the catalog, because the same tool is how the model re-enters a helper it spawned; the gate is on the argument, not on the name.
- The model calls `ListAgents` → it succeeds and returns human-readable text naming this run's peer identity and the user's other sessions. Nothing in the adapter parses it, and no unified event is derived from it.
