# Brief: 0.0.7 → 0.0.8

This release gives the library a **hard, runtime SDK-version contract**. Until now every adapter only detected whether its wrapped agent SDK was *installed* (a lazy `import()` that fails as `AdapterInitError` when missing); it never checked *which version*. 0.0.8 adds a new compatibility discipline: at init each consumer that wraps a peer-SDK reads the installed version, checks it against a **narrow, verified** range, and hard-fails when it falls outside — so a subtly incompatible SDK can no longer produce silently wrong behavior. The same release narrows the over-wide `peerDependencies` ranges to the verified ones (one of them a breaking narrow), and consolidates task/todo tracking into a single documented projection matrix that serves as the flagship example of tolerated in-range schema drift.

<!-- anchor: version-gate -->
## New: hard peer-SDK version gate at init

Every peer-SDK consumer — the four adapters plus MCP integration — now performs a **blocking version check** at init:

1. Read the installed peer-SDK `package.json` `version` (via `createRequire` / `require.resolve` to the package manifest; fall back to the nearest resolvable manifest if the package's `exports` map hides `package.json`).
2. Evaluate `satisfies(installedVersion, supportedRange)`.
3. On mismatch, **emit** (never throw) an `error` event with `phase: 'init'` — an `AdapterInitError` whose message names *installed X, requires Y*. It is **non-suppressible**: no `warning` fallback, no config gate, no bypass.

This is distinct from the existing *availability* probe (a missing SDK) — absence and wrong-version are two separate init faults, both surfaced as `AdapterInitError`. The version gate runs immediately after a successful `import()`. For opencode there is also a separate CLI probe (`isOpencodeAvailable()` → `which opencode`) that gates on the `opencode` binary; an out-of-range SDK and a missing binary stay distinct faults (the adapter drives a spawned server, so a compatible SDK and an incompatible CLI can coexist).

The supported ranges (each **equals** the range verified in CI — declaring `>=x` while testing a single pin is explicitly forbidden):

| Consumer | Peer SDK | Supported range | dev-pinned |
| --- | --- | --- | --- |
| claude-code (A01) | `@anthropic-ai/claude-agent-sdk` | `>=0.3.0 <0.4.0` | `^0.3.153` |
| codex (A02) | `@openai/codex-sdk` | `>=0.120.0 <0.121.0` | `^0.120.0` |
| opencode (A03) | `@opencode-ai/sdk` | `>=1.4.0 <2.0.0` | `^1.4.6` (+ additive `@opencode-ai/sdk/v2/client`) |
| gemini (A04) | `@google/gemini-cli-core` | `>=0.38.0 <0.39.0` | `^0.38.0` |
| MCP integration (M04) | `@modelcontextprotocol/sdk` | `>=1.0.0 <2.0.0` | `^1.29.0` |

Notes: MCP keeps a full-major `1.x` range because its 1.x line has been stable/additive; `gemini-cli-core` is the fastest-moving peer, so its narrow range matters most. The `@modelcontextprotocol/sdk` peer is owned by no adapter, so MCP integration (a capability-module, not an adapter) hosts its gate; its SDK is loaded lazily only when in-process `sdk` MCP servers or the `createMcpServer` / `mcpTool` builders are used.

One open implementation caveat carried in the spec: confirm the `@anthropic-ai/claude-agent-sdk` `package.json` is actually reachable (not blocked by its `exports` map) before wiring the claude-code gate.

## Breaking: `peerDependencies` narrowed to the verified ranges

The `package.json` `peerDependencies` entries must be narrowed to match the ranges above (the range in the spec is authoritative; `package.json` mirrors it). Most are tightening an over-wide lower/upper bound to what is actually tested. **One is a breaking change for consumers:** claude-code's peer entry goes from today's over-wide `>=0.2.0` to `>=0.3.0 <0.4.0`. A consumer still pinned to `@anthropic-ai/claude-agent-sdk` 0.2.x will now hit the hard init gate. This ships as a deliberate semver call, not silently.

## In-range schema drift: defensive reads (two regimes)

The gate draws a hard line between two regimes:

- **Outside** the declared range → hard init failure (the gate above).
- **Inside** the declared range → the adapter commits to keep working across tool/field renames by **reading defensively**: dual-path reads over `Record<string, unknown>` across known field aliases, so a renamed field degrades to a correct projection or a documented gap, never a silent no-op or crash.

Two new acceptance criteria formalize this:

> When an installed peer-SDK version falls outside a consumer's declared range (any adapter, or MCP integration for `@modelcontextprotocol/sdk`), init emits an `error` event with `phase: 'init'` (`AdapterInitError`) naming installed-vs-required — a hard, non-suppressible failure.

> When a peer-SDK's tool or field schema drifts *within* the declared range, the adapter reads defensively (dual-path over `Record<string, unknown>`) and keeps producing correct output — a renamed field degrades gracefully and is never a silent no-op.

Currently only claude-code has a concrete named drift point (below); codex, opencode, gemini and MCP declare "none identified in-range yet" honestly, naming their most exposed surfaces (codex: JSONL `item.completed` shapes + `turn.completed.usage`; opencode: `message.part.updated` discriminants + additive v2 `question.asked`; gemini: `AgentEvent` thought/usage/`agent_end` shapes + `Config` surface; MCP: `McpServerConfig` transport shapes).

## Task / todo tracking consolidated into one matrix

Task/todo tracking is now documented in one place as the **flagship in-range drift case** — the reference scenario the defensive-read discipline exists for. The reference drift: claude-code's SDK replaced the full-list-replace `TodoWrite` tool (removed ~0.2.82) with a per-item CRUD family `TaskCreate` / `TaskGet` / `TaskUpdate` / `TaskList` — a tool rename *without* a major bump. Every engine's task tool is projected onto one `todo_list_updated` event plus an accumulating todo snapshot:

| Adapter | Task-tracking source | `todo_list_updated` `source` | Snapshot accumulation |
| --- | --- | --- | --- |
| claude-code (A01) | `TaskCreate` / `TaskGet` / `TaskUpdate` / `TaskList` per-item CRUD (in-range), gated behind a `ToolSearch` discovery call on newer models; legacy `TodoWrite` full-list-replace kept only as an out-of-range defensive read | `model-tool` | CRUD family: **per-item merge**; legacy `TodoWrite`: **wholesale replace**. The echoed `tool_result` is suppressed as redundant. |
| opencode (A03) | `todo.updated` SSE frame | `session-state` | **Wholesale replace** from session state; also projected into a synthetic assistant message so `rawMessages` carries the todo history. |
| codex (A02) | — (SDK exposes no task-tracking tool) | — | No `todo_list_updated` emitted — documented absence, never a silent pretense. |
| gemini (A04) | — (SDK exposes no task-tracking tool) | — | No `todo_list_updated` emitted — documented absence, never a silent pretense. |

The claude-code defensive read walks a dual path across the legacy and CRUD field names (`subject` / `description` / `taskId`). Because absence-of-tool is not a consumer-requested capability, codex/gemini emitting nothing is a documented no-op, not a warn/skip degradation.

**Known debt now documented:** a `TaskUpdate` with `status: "deleted"` should remove the item from the snapshot, but the current merge keeps it — consumers must not assume a deleted item disappears.

## For implementers

Ordered by dependency:

1. **Add a shared version-gate helper.** Given a peer package name + a supported semver range, resolve the installed `package.json` `version` (`createRequire(import.meta.url)` / `require.resolve('<pkg>/package.json')`, with a fallback that walks to the nearest resolvable manifest when the `exports` map hides `package.json`), then `satisfies(version, range)`. On mismatch, **emit** an `error` event `{ phase: 'init' }` as an `AdapterInitError` with message `installed <X>, requires <range>`. Do not throw; do not add a config bypass. (Error surface owned by M13 `AdapterError`.)
2. **Wire the gate into each adapter's init/`execute()` path, right after the successful lazy `import()`**, using these ranges:
   - claude-code: `@anthropic-ai/claude-agent-sdk` `>=0.3.0 <0.4.0`. First verify the package's `package.json` is reachable through its `exports` map; if not, use the manifest-walk fallback.
   - codex: `@openai/codex-sdk` `>=0.120.0 <0.121.0`.
   - opencode: `@opencode-ai/sdk` `>=1.4.0 <2.0.0` (keep the existing `isOpencodeAvailable()` / `which opencode` CLI probe as a *separate* fault; also keep the `@opencode-ai/sdk/v2/client` import with its v1 fallback).
   - gemini: `@google/gemini-cli-core` `>=0.38.0 <0.39.0` (runs alongside the existing missing-exports check).
3. **MCP integration** — apply the same gate for `@modelcontextprotocol/sdk` `>=1.0.0 <2.0.0` where the MCP SDK is lazily loaded (in-process `sdk` servers / `createMcpServer` / `mcpTool`).
4. **`package.json` — narrow `peerDependencies`** to the five ranges in the table above. `@anthropic-ai/claude-agent-sdk` moving from `>=0.2.0` to `>=0.3.0 <0.4.0` is a **breaking** change — bump the library's own version accordingly and note it in the changelog.
5. **Preserve task-tracking behavior** while touching the adapters: claude-code must keep the `TodoWrite` ↔ `TaskCreate/TaskGet/TaskUpdate/TaskList` dual-path read over `Record<string,unknown>` (`subject` / `description` / `taskId`), the `ToolSearch` discovery gate, per-item snapshot merge (CRUD) vs. wholesale replace (`TodoWrite`), and `model-tool` as the `todo_list_updated` `source`; opencode keeps `todo.updated` → `session-state` wholesale replace + synthetic assistant message.
6. **Optional follow-up** (documented debt): make the snapshot merge honor `TaskUpdate { status: "deleted" }` by removing the item.
