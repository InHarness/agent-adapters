# Brief: 0.9.1 → 0.9.2

<!-- anchor: b0summary -->
## Summary

This release hardens how `@inharness-ai/agent-adapters` handles **turns that outlive their `result`** — the Claude Code case where the engine keeps a session alive after a turn ends (backgrounded shell work *or* a subagent that finishes late), wakes the model, and produces a further `result`. 0.9.1 already had the background-task lifecycle; 0.9.2 fixes the edge cases that made it wrong in practice: subagents were not being held/tracked the way backgrounded shells were, the in-flight signal leaked subagents, the hold bounds could fire mid-wake-up and cut the control channel, and the SDK's real wire spellings (`local_bash`, display-label `'subagent'`) were assumed rather than observed. Two adjacent correctness fixes ride along: task-tracking create→update now reconciles to one item via the create's `tool_result`, and MCP form-elicitation is documented as refused by the engine's own MCP client. All behavior lives in the Claude Code adapter and the unified layer; no entity/schema changes, no new endpoints or tables.

Everything below targets `src/adapters/claude-code.ts`, `src/types.ts` (the `UnifiedEvent` union), and a few consumer/test helpers. Concrete edit targets are in **For implementers** at the end.

## Unified contract: `result` is not always terminal, `warning` is side-band

The unified event contract (M01, `src/types.ts`) is tightened so consumers stop treating the first `result` as end-of-run:

- **`result` gains an in-flight signal.** A `result` event now carries:

  ```ts
  backgroundTasks?: Array<{ taskId: string; taskType: string }>  // empty/absent = truly terminal
  ```

  When non-empty, the underlying session stays alive waiting for background work to settle; on settlement the engine wakes the model, which continues and produces a further `result`. **Consumers must iterate `execute()` to generator `done`; the first `result` is not end-of-run.** This list carries engine-backgrounded work **only — never a subagent** (see the split below).

- **The background-task lifecycle events are first-class in the taxonomy** (semantics owned by M17, decoupled from `subagent_*`):

  ```ts
  background_task_started   { taskId, taskType, description }
  background_task_progress  { taskId, taskType, status?, outputFile? }
  background_task_completed { taskId, taskType, status, outputFile?, summary?, usage? }
  ```

  `taskType` is the **unified** vocabulary consumers see: `'shell'` | `'monitor'` | `'workflow'`. It is **not** the SDK's on-the-wire discriminator — each adapter maps its own spelling onto these names (see the `local_bash` note below). `outputFile`, when present, is a file path the engine streams the process's stdout into; consumers tail it for live output, the unified stream carries lifecycle only.

- **`warning` is side-band and may follow the terminal `result`.** A `warning` reports on the run rather than advancing it, and adapters may raise one from a timer callback (the hold bounds below fire *after* the last `result`). So **"`result` is terminal" now means the last non-`warning`, non-`flush` event.** Any conformance check asserting the literal last event is `result` is wrong — `flush` already had this exemption; `warning` joins it.

## Background-task hold: subagents hold too, but are never reported

The core behavioral fix. Previously the adapter effectively treated "hold the session" and "report in `result.backgroundTasks`" as the same decision, and tracked backgrounded shells but not late subagents. 0.9.2 separates the two:

- **Both kinds are tracked in the in-flight set.** A late-settling **subagent** can outlive the turn's `result` exactly like a backgrounded shell — this is the shape of the original bug report. Two signals move a task through the tracked set:
  - `task_updated` carrying a **terminal `patch.status`** marks a task *finished* (distinguishes "still working" from "done, wake-up pending" — which decides which hold bound applies).
  - `task_notification` **removes** it from the set and emits the completion event.

  Measured on SDK 0.3.153 and 0.3.210: `task_updated` precedes its `task_notification` by milliseconds, and both fire for subagents as well as backgrounded shell work.

- **Holding is not reporting.** The tracked set drives the **control-channel hold** for *both* kinds — a subagent holds the session just as a backgrounded command does. But it populates `result.backgroundTasks` for **background kinds only**. Listing a subagent there would promise a `background_task_completed` that never arrives, hanging a consumer that correctly iterates to `done`. Real subagents stay on the `subagent_*` lifecycle (M06); `subagent_*` is now explicitly scoped to *actual spawned helper agents only*.

- **Display labels must be classified, not passed through.** Claude Code's `BackgroundTaskSummary.type` is a **display label**, and on 0.3.210 it is literally `'subagent'` for helper agents. Passing it through unclassified both leaks subagents into `result.backgroundTasks` and mislabels `local_bash`. Every entry — whether from the adapter's own tracking or an engine-supplied list — must be classified through the same `task_type` mapping first, and engine lists are **unioned** with the tracked set, never substituted for it.

- **The `Stop` hook is a positive signal only.** The adapter registers a `Stop` hook (additively, alongside the disable-lever `PreToolUse` hook and project hooks) to read `StopHookInput.background_tasks`. Measured both pins: it fires ~3ms *before* the `result` it belongs to, and a **non-empty** answer is exact → hold. An **empty** answer is *not* trustworthy: on 0.3.153 a three-subagent run reported `[]`, after which the engine held the session, woke the model 2ms later, and ran a full further turn (0.3.210 does list subagents there). So it is consumed as a positive hold reason only, unioned with the adapter's own tracking, and **never as permission to close**.

## Wire spellings are observed, not assumed (`local_bash`)

The unified `taskType` values (`'shell'`/`'monitor'`/`'workflow'`) are **not** what the SDK sends. Live against 0.3.153, a `run_in_background` Bash command reports `task_type: 'local_bash'` — not `'shell'`; the SDK prefixes locally-executed kinds with `local_` (`local_workflow` appears alongside `workflow_name`). **The adapter must strip the `local_` prefix before mapping.** The SDK type declares only `task_type?: string`, so any table of kinds must be checked against a live probe, never inferred from the types. Unknown/absent `task_type` still defaults to the subagent path (legacy behavior), so an SDK that stops sending the discriminator degrades to the pre-M17 shape rather than misrouting.

## Hold bounds: neither may fire while the model is producing

The hold is bounded twice so it can never become a hang (`sleep 3600 &`, or an SDK that drops the wake-up). 0.9.2 rewrites both bounds so a bound can never fire mid-wake-up (which would close the very control channel the hold protects):

- **Grace window** — armed only once *everything tracked has settled* (the sole outstanding thing is then a wake-up), and **re-armed by every frame that arrives while parked**, so it measures engine *silence*. The engine really does emit `system/status` and `system/background_tasks_changed` frames while babysitting work; the previous version let any one of them disarm the grace outright. Subagent chatter (`parent_tool_use_id` set) is not a resumption and does not release it.
  - **Grace sizing is empirical.** It must exceed the gap between the last task settling and the first frame of the continuation turn. Measured with `includePartialMessages` (always set): **3.5s** (backgrounded bash) and **3.7s** (three subagents) on 0.3.210; **5.0s** on 0.3.153 without partials. A 5s window had no margin. **Default is set to 15s** (~4× the worst observed), re-measured whenever the peer range moves.
  - **Grace expiry is silent** — settled work + a quiet engine is how a healthy task-touching run *ends*. A `warning` there would fire on the happy path of every run that so much as spawned a subagent: a false, noisy data-loss report.

- **Cap** — a hard bound on the parked stretch, for work still running that may never finish. **Released the instant a continuation turn's first main-model frame arrives** (from there the run is an ordinary live turn bounded by `timeoutMs`/`abort()`). **Only cap expiry emits a `warning`** (naming the bound) — it can only expire with something genuinely unsettled, so its warning is truthful.
  - **The cap default is 90s, deliberately under the 120s default of the library's own `collectEvents()` helper.** The two clocks race and the consumer's timeout starts *earlier* (at run start, not at the held `result`), so a cap ≥ the consumer timeout can never emit its truncation warning — the helper rejects the run first and the abandonment signal is lost. The lever docs say to raise both together.

- **Both bounds are consumer-tunable** via adapter-prefixed `architectureConfig` keys (L3):

  ```
  claude_backgroundGraceMs      // default 15000
  claude_backgroundHoldCapMs    // default 90000
  ```

  The grace is dead time paid at the end of **every** task-touching run (including one whose subagents all finished in-turn), so a consumer on a tight wall-clock budget must be able to buy it back without forking the adapter. A value that is **not a finite number > 0 degrades to the default** — `0` would disarm a bound whose whole purpose is keeping the control channel open, so "invalid" must never mean "no bound".

## Abort teardown must not await `Query.interrupt()`

The M13 abort guarantee is now explicitly **behavioural** — it must not depend on cooperatively interrupting the engine. Teardown on `abort()`/timeout is:

1. Fire the abort signal (breaks every awaited point, including a raced `await` on the consumer's `onUserInput` handler a UI-backed consumer may never resolve).
2. Answer the outstanding user-input request `cancel` (so the SDK-side promise settles instead of leaking).
3. Close the input channel.

After which the run yields `AdapterAbortError` / `AdapterTimeoutError` with no dangling SDK subprocess. **`Query.interrupt()` must never be awaited on the teardown path** — it is a control-protocol round-trip over the *same* stdin that teardown then closes, so awaiting it can outlive its transport and never settle, reintroducing exactly the parked-run failure M13 exists to prevent. If called at all it is strictly **fire-and-forget**; a rejecting, synchronously-throwing, or entirely absent `interrupt()` must still terminate the run. It is now merely *available* on every run (the input channel is universal), not *required*.

## Task-tracking: create→update must reconcile to one item

Correctness fix in the task-tracking projection (M16; the Claude Code `TaskCreate/TaskGet/TaskUpdate/TaskList` CRUD family that replaced `TodoWrite`):

- In a per-item CRUD family the **create call carries no identifier** — the engine assigns one and reports it in the create's **`tool_result`** (verbatim `"Task #1 created successfully: <subject>"` on both 0.3.153 and 0.3.210). Every later `TaskUpdate({ taskId, status })` keys on that assigned id. A projection built from tool *inputs* alone has nothing to match on, so the update lands as a **second, blank-titled item** and the real item's status never moves.
- The projection **must recover the assigned id from the create's `tool_result`** and alias it to the item that call produced. This is the one place the family's `tool_result` carries information its input does not; it is read for the identifier only, and the payload stays suppressed as redundant.
- **Recovery must not rest on one English sentence** (the id is announced in unstructured prose — a single reworded CLI string would silently reinstate the bug). It is a *known weak contract*; the durable fix is upstream (a structured `tool_result`). Until then, reduce the blast radius three ways:
  1. Prefer any **structured identifier** in the payload over prose.
  2. Accept **several plausible phrasings**, rejecting captures that are obviously sentence words rather than identifiers.
  3. Keep a **deterministic positional fallback** — with exactly one unreconciled create and an update naming an id never seen assigned, they can only be the same task. **Ambiguity (two+ unreconciled) is left alone**, not guessed (a wrong alias corrupts a real item; a missing one merely appends a stray one). Any unresolved case is logged behind the debug flag so the next regression is visible, not silent.

## MCP form-elicitation is refused by the engine's own client

Documented reality for M04, not a code change to the bridge (which stays in place):

- An in-process SDK-MCP server calling `elicitInput({ message, requestedSchema })` resolves to **form** mode and, on `@anthropic-ai/claude-agent-sdk` 0.3.153 (measured 2026-07-27), is rejected **inside the MCP layer** with `Client does not support form elicitation`. No `elicitation/create` is forwarded, so **`onElicitation` / `user_input_request { source: 'mcp-elicitation' }` never fires**, no matter how the adapter is wired.
- The server sees the throw as its own tool error; the model then typically recovers by asking through whatever ask-user tool it has, which arrives as `source: 'model-tool'`.
- **Two consequences for tests:** a correct adapter-side bridge does *not* imply the path is live end-to-end, and **any live test must key on `source: 'mcp-elicitation'` specifically** — keying on "a user-input request happened" reads the model's `model-tool` fallback as a false pass. The e2e for it self-skips with the refusal message rather than pretending to pass. (url-mode elicitation is untested.)

## Usage: `result.usage` is always that turn's own cost

Clarified invariant across M08/M01 and the Claude Code adapter:

- **`result.usage` is always that turn's own cost, never a running total.** Adapters whose SDK reports *cumulative* session usage must subtract to a delta before emitting (M08's `priorUsage` mechanism — this is the **codex** case). Claude Code already reports per-turn cost, so no delta subtraction is needed there.
- Several `result`s in one `execute()` is **normal, not exceptional** — a mid-turn `pushMessage` runs as another turn (M11), and a background-work wake-up produces a further `result` (M17). So a run's billing is the **sum** of its `result`s, and `contextSize` is the **last** one, never a sum. (Verifiable on Claude Code: measured across both pins, a run's second `result` reports fewer tokens than its first in every field — which a running total cannot do.)

## Shipped helpers and conformance must honour the in-flight signal

The in-flight rule binds the library's own exports, not just external consumers:

- **Stream helpers that stop early** (M09 — `takeUntilResult()`, and anything ending consumption on a `result`) must treat a `result` carrying a non-empty `backgroundTasks` as **not** terminal and keep going. A shipped helper that stops at the first `result` hands everyone reaching for the ergonomic path the precise bug the signal was added to prevent, while looking like the endorsed way.
- **The conformance toolkit** (M12, `testing/contract.ts` / `testing/e2e/shared.ts`) exempts side-band events from ordering assertions: its terminality check reads the **last non-`flush`, non-`warning`** event. A toolkit demanding a literal trailing `result` would fail conforming adapters (a `warning` can legitimately follow it). Same exemption `adapter_ready` already makes at the *start* of the stream.

## For implementers

All work is in `@inharness-ai/agent-adapters`. Ordered roughly by dependency.

1. **`src/types.ts` — `UnifiedEvent` union & `result`:**
   - Ensure `result` carries `backgroundTasks?: Array<{ taskId: string; taskType: string }>` (empty/absent = terminal; background kinds only).
   - Ensure the background-task lifecycle variants exist and are decoupled from `subagent_*`: `background_task_started { taskId, taskType, description }`, `background_task_progress { taskId, taskType, status?, outputFile? }`, `background_task_completed { taskId, taskType, status, outputFile?, summary?, usage? }`, with `taskType: 'shell' | 'monitor' | 'workflow'`.
   - Add `claude_backgroundGraceMs` / `claude_backgroundHoldCapMs` to the `architectureConfig` key surface (alongside existing `claude_disallowBackgroundBash`).

2. **`src/adapters/claude-code.ts` — background-task hold (the bulk):**
   - Maintain a `Map<task_id, task_type>` populated on `task_started`; route later `task_progress`/`task_notification` (which lack `task_type`) through it.
   - **Strip the `local_` prefix** from `task_type` before mapping (`local_bash` → `shell`, `local_workflow` → `workflow`). Unknown/absent → subagent path.
   - Track **both** subagents and backgrounded shells in the in-flight set: `task_updated` with terminal `patch.status` → mark finished; `task_notification` → remove + emit completion.
   - Drive the control-channel hold from the full tracked set (both kinds); populate `result.backgroundTasks` from **background kinds only** — classify every entry (including engine `BackgroundTaskSummary.type`, which is `'subagent'` for helpers) through the `task_type` mapping; union engine lists with local tracking, never replace.
   - Register a `Stop` hook to read `StopHookInput.background_tasks` as a **positive hold signal only** (empty ≠ close).
   - Rewrite the two bounds: **grace** armed only when everything tracked is settled and re-armed by every parked frame (default 15000ms, silent on expiry); **cap** released on the continuation turn's first main-model frame (default 90000ms, `warning` on expiry). Neither may fire while the model produces frames. Invalid lever values (not finite > 0) fall back to defaults. Keep cap default below `collectEvents()`'s timeout.
   - Keep the seeded input channel open while the tracked set is non-empty; close on the continuation `result` once it drains.

3. **`src/adapters/claude-code.ts` — abort/timeout teardown:**
   - Teardown = fire abort signal → answer outstanding user-input `cancel` → close input channel. **Do not `await Query.interrupt()`** — call it fire-and-forget or not at all; tolerate reject/throw/absent. Emit `AdapterAbortError` / `AdapterTimeoutError`.

4. **`src/adapters/claude-code.ts` — task-tracking projection (M16):**
   - Recover the engine-assigned task id from the **create's `tool_result`** (prose `"Task #1 created successfully: <subject>"`), alias it to the created item so `TaskUpdate({ taskId })` mutates the right item instead of appending a blank-titled one. Prefer structured id if present; accept several phrasings; deterministic positional fallback only when exactly one create is unreconciled; leave ambiguous (2+) cases alone; log unresolved cases behind the debug flag. Keep the create's `tool_result` payload suppressed otherwise.

5. **`src/adapters/codex.ts` — usage:** confirm cumulative session usage is subtracted to a per-turn delta before emit (`priorUsage`); Claude Code needs no subtraction.

6. **Stream helpers (M09, e.g. `src/stream`/observers):** make `takeUntilResult()` and any early-stopping helper treat a `result` with non-empty `backgroundTasks` as non-terminal and continue to `done`.

7. **`testing/contract.ts` / `testing/e2e/shared.ts` (M12):** terminality check must read the **last non-`flush`, non-`warning`** event; do not require a literal trailing `result`.

8. **`src/testing/e2e/claude-code.e2e.test.ts`:** the MCP form-elicitation test must key on `source: 'mcp-elicitation'` and **self-skip** on `Client does not support form elicitation` (0.3.153) rather than accept the `source: 'model-tool'` fallback as a pass.
