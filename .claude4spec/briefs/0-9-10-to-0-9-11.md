# Brief: 0.9.10 → 0.9.11

This release gives a run a **second clock**. Until now the only time bound an adapter armed was `timeoutMs` — a wall-clock budget on the whole `execute()` call — which answers "has this run taken too long?" but says nothing about a run that is alive and producing nothing. 0.9.11 introduces `idleTimeoutMs`, a clock that advances *only while the engine owes the consumer something and is silent about it*, and in the same stroke tightens the contract of `timeoutMs` (armed once at run start, never re-armed, and with **no fallback default** when omitted). The point is to let a consumer detect a stalled engine without killing a run that is legitimately waiting — on a slow tool, on a subagent, on a background task, or on a human.

A second, unrelated thread in this release: the claude-code adapter's SDK version pin `^0.3.251` was moved out of "pending verification" and probed live.

## The new field: `idleTimeoutMs`

`RuntimeExecuteParams` gains:

```ts
idleTimeoutMs?: number;
```

The model behind it is that a run is, at every moment, in exactly one of two states:

- **nothing outstanding** — the engine owes the consumer something, so silence is a stall;
- **work in flight** — something legitimate is pending, so silence is healthy.

**The idle clock advances only in the "nothing outstanding" state.** It is explicitly *not* a "re-arm on last sign of life" timer — that design is named and rejected in the spec, on the grounds that "silence means nothing on its own". The corollary is stated too: a pause with nothing outstanding *is* idleness however short it is, and the clock does not care what preceded it.

"Outstanding work" is an enumerated, closed list — this is the surface an implementer checks before deciding whether to advance the clock:

1. a `tool_use` with no matching `tool_result` yet;
2. a subagent still open (M06);
3. a background task not yet settled (M17);
4. an unanswered `user_input_request` — "a human being slow rather than an engine gone quiet";
5. a nested turn the consumer started from inside the run.

Outstanding work is not therefore unbounded: while something is outstanding, the run is bounded by *that work's own cap* (M17's control-channel hold cap being the existing instance of this shape). Without that rule a hung tool call would simply wait out the backstop.

Omitting `idleTimeoutMs` means there is no idle clock at all and the run behaves exactly as in 0.9.10.

## `timeoutMs` is the absolute backstop — and its absence is a guarantee

The existing `RuntimeExecuteParams.timeoutMs?: number` did not change shape, but its contract is now written down unambiguously:

- It bounds the **whole `execute()` call, measured from run start**.
- It is **armed exactly once and never re-armed**. No event, frame, tool result or progress notification moves it. This is by design, not a gap.
- On expiry the run ends with `AdapterTimeoutError`, reported in the **runtime** phase.
- Under `streamingInput: true` the unit of arming is still the single `execute()` call: one backstop and one idle clock span the entire streaming session, run through the idle gaps between pushes, and cover every `result` yielded. **A `pushMessage()` call buys no fresh budget.**
- Omission is now a promise, not a default. Verbatim from the spec: *"Omitting the field is a guarantee, not a default: there is no fallback value and no timer at all on any adapter, so the run carries no wall-clock bound."* Implementers must not invent a default `timeoutMs`.

One standing exception survives: M17's control-channel hold cap ends a run regardless of `timeoutMs`, because it is armed at a **held `result`**, not at run start, and it bounds only the parked stretch — and only on adapters that actually hold the channel open. A run that never holds and sets no `timeoutMs` is bounded only by `abort()`.

## Four clocks, all adapter-side

The spec now names the full set so they stop being confused with one another:

| Clock | Armed at | Re-arms? | Expiry |
| --- | --- | --- | --- |
| Backstop — `timeoutMs` | run start | never | terminal, `AdapterTimeoutError` |
| Idle clock — `idleTimeoutMs` | advances only while nothing is outstanding | stops (does not advance) while work is in flight | terminal, `AdapterIdleTimeoutError` |
| Hold grace window (M17) | once everything tracked has settled | re-armed by every frame while parked | **silent** |
| Hold hard cap (M17) | a held `result` | never | terminal, via M13's error classes |

All four are adapter-side. A consumer-side timer — such as `collectEvents()`'s own default in M09 — is explicitly *not* one of them. `abort()` is explicitly *not* a fifth clock: it is "the consumer's hand on the same switch".

## New error class: `AdapterIdleTimeoutError`

M13's `AdapterError` hierarchy grows by one:

- `AdapterIdleTimeoutError` — `idleTimeoutMs` exceeded; the run fell idle with nothing outstanding. Runtime phase, terminal, and distinguishable both by `instanceof` and by `.name`, like every other class in the hierarchy.
- `AdapterTimeoutError`'s description is now qualified as *"`timeoutMs` exceeded — the absolute backstop"*.

The counts in M13's prose move with it: "Three of the four above" end a live run becomes **"Four of the five above"**, and `AdapterToolPolicyError`'s "The other four end or fail a live run" becomes **"The other five"**.

The two timeout errors are deliberately kept apart because they mean different things to a caller: an `idleTimeoutMs` expiry "says something different in kind — not that the run outlived its budget but that it went quiet while still owing the consumer something, a stall to diagnose rather than a limit to raise." A backstop expiry invites you to raise the limit; an idle expiry invites you to go find what hung.

M13's edge-case list gains the matching bullet: `idleTimeoutMs` expires → `AdapterIdleTimeoutError` (runtime phase), and the SDK run is stopped down the same path as a backstop expiry. M13 owns only the *outcome* (terminal, typed apart from the backstop, runtime phase); what makes the clock advance and what stops it is M01's to define.

## Where the idle clock is explicitly excluded

Three modules had their termination rules amended so the exclusion is not left to inference:

- **Unanswered `user_input_request` (M11/M13).** The existing rule about `abort()` and `timeoutMs` racing an open `onUserInput` is now scoped: *"Those two and no other clock: an unanswered request is outstanding work — a human being slow, not an engine gone quiet — so `idleTimeoutMs` does not advance while one is open and can never be what ends such a run."* The rest of that path is unchanged: `onUserInput` races the abort signal, an outstanding request is answered with `cancel`, the stream yields `AdapterAbortError` / `AdapterTimeoutError`, teardown runs.
- **Open subagent (M06).** The list of things that can cut a subagent short — `abort()`, `timeoutMs`, hold-cap expiry — is now declared **complete**, with the idle clock missing from it on purpose: an open subagent is outstanding work, so `idleTimeoutMs` does not advance while one is running and can never be what cuts it short. The existing behaviour is untouched: on termination the adapter synthesizes a closing `subagent_completed { status: 'aborted' }` for every `subagent_started` still unpaired, at most once per `taskId`, and a subagent that already produced its own terminal event is not closed twice.
- **In-flight background task (M17).** The dependency on M13 was one line and is now two rules. Before: *"A whole-run `timeoutMs` / `abort()` still bounds a run with in-flight background work."* After, that sentence continues: *"— and ends it with M13's classes, the hold cap's own expiry included. `idleTimeoutMs` is the clock that does **not**: a background task not yet settled is outstanding work, so the idle clock does not advance while this module's work is in flight."*

## M06 gains two L4 exports

The subagents module's public surface grows:

```
before: exports SubagentDefinition, validateSubagents
after:  exports SubagentDefinition, SubagentStatus, validateSubagents, mapSubagentStatus
```

`SubagentStatus` is the type and `mapSubagentStatus` the function that normalises an engine's own subagent status vocabulary onto it — the shape adapters other than claude-code need in order to emit unified `subagent_completed` events.

## New acceptance criteria

Four criteria were added against M01 (three as edge cases, tagged `m01` + `m01-edge`; the fourth as a requirement, tagged `m01`). Verbatim:

1. *A run parked on an unanswered user_input_request does not expire on the idle clock: idleTimeoutMs does not advance while the request is open, however long the human takes to answer.* (edge case)
2. *A run that keeps emitting events for longer than timeoutMs still terminates at that budget measured from run start: no event, frame, tool result or progress notification re-arms the backstop.* (edge case)
3. *A run whose only activity is a single tool_use still awaiting its tool_result does not expire on the idle clock, however long the tool takes, because an unmatched tool call is outstanding work and idleTimeoutMs does not advance while it is open.* (edge case)
4. *With timeoutMs absent no adapter arms a wall-clock timer and no fallback default applies, so elapsed time alone never ends a run — a bound armed on something other than run start, such as M17's background hold cap, is unaffected.* (requirement)

## For implementers

Ordered roughly by dependency — types first, then the runtime that consumes them.

1. **Add the error class** (M13's L1 section). `AdapterIdleTimeoutError extends AdapterError`, runtime phase, distinguishable by `instanceof` and by `.name` like its siblings, and carrying its extra fields through `toJSON()`. No fields beyond the hierarchy's standard ones are specified.

2. **Add the option to the params type** (M01's L1 section): `idleTimeoutMs?: number` on `RuntimeExecuteParams`, alongside the existing `timeoutMs?: number`. Both optional; both absent means no bound of either kind.

3. **Implement the outstanding-work tracker** in the shared runtime path. It needs a counter or set that is non-empty while any of these hold, and the idle timer must be paused (not reset) for exactly that period:
   - a `tool_use` id with no matching `tool_result` yet;
   - an open subagent (a `subagent_started` with no paired `subagent_completed`, keyed by `taskId`);
   - an unsettled background task;
   - an emitted `user_input_request` with no answer yet;
   - a nested consumer-started turn.

   When the set empties, start/resume the idle clock; when it becomes non-empty, stop it. Do **not** restart it on arbitrary events — this is not a last-activity timer.

4. **Audit the backstop's arming site.** `timeoutMs` must be armed once, at the top of `execute()`, and never touched again — in particular verify that no event handler, `pushMessage()` path, tool-result handler or progress-notification handler calls anything that resets it. Under `streamingInput: true` the same single timer must span the whole session across all `result` events.

5. **Remove any fallback default for `timeoutMs`.** Absent must mean *no timer is created at all*, on every adapter. Grep each adapter's option-mapping for a default value or an `?? DEFAULT_TIMEOUT` shape and delete it. `abort()` and M17's hold cap are then the only things that can end an unbounded run.

6. **Keep the hold cap independent.** M17's hard cap arms at a held `result` and must keep firing even when `timeoutMs` is absent; its expiry is terminal and reported with M13's classes. The hold's *grace window* keeps its existing shape — re-armed by every frame while parked, expiring silently.

7. **Export the subagent status mapping** from M06's L4 surface: the `SubagentStatus` type and the `mapSubagentStatus` function, next to the existing `SubagentDefinition` and `validateSubagents`.

8. **Do not let the idle clock terminate anything it is excluded from.** Add regression coverage for the three exclusions: a run parked on `onUserInput`, a run with an open subagent, and a run with an unsettled background task — each with a short `idleTimeoutMs` — must all survive well past that value and only end via `abort()`, `timeoutMs`, or the relevant work's own cap.

9. **claude-code adapter**: the dev pin `^0.3.251` is confirmed at `0.3.263` / CLI `2.1.263`. When touching the background-task wake-up path, note that subagents no longer appear in `StopHookInput.background_tasks` on this pin, so the union-and-grace path is currently unexercised for the subagent kind — do not treat its green scenario result as coverage. The remaining `test:e2e:claude:*` model scripts are still unrun.
