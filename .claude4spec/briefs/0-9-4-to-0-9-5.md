# Brief: 0.9.4 → 0.9.5

This release moves the claude-code adapter's background-task support from "asserted by construction" to "measured against a live model". It introduces a new named end-to-end scenario, `background-tasks`, defined as a 2×2 wake-up matrix, and promotes it into the cross-adapter scenario vocabulary so every adapter is now judged against it (or explicitly skips it). Alongside that, a batch of claude-code e2e gaps that had been carried as `planned` for several releases is closed — image input, mid-turn `pushMessage`, path scoping, usage accounting, MCP elicitation, and the `timeoutMs` resilience path — while the SDK-version gate is split out as a still-open item so it stops hiding inside a green row.

No runtime contract changed in this window: no new events, no new options, no support-matrix cell flipped, no degradation rule rewritten. The deliverable is verification — a real test suite that proves the behaviour that 0.9.x already claimed.

## The `background-tasks` scenario is now part of the canon

`background-tasks` joins the cross-adapter scenario catalog, right after `mid-turn` and before `abort`. It is the vocabulary term every adapter's coverage table must answer for. The canonical definition of the scenario:

> `background-tasks` — engine-backgrounded work outliving the turn is observed end-to-end: the lifecycle family is emitted, the first `result` is **not** terminal, the engine's wake-up produces a continuation turn and a further `result` before `done`, and the control channel is still live across the hold. Absent on adapters whose SDK never backgrounds work.

The "absent" clause matters: adapters whose underlying SDK cannot background work (codex, gemini, opencode) do not fail this scenario — they skip it, per the existing background-tasks skip strategy. Only claude-code (via the SDK's `run_in_background` bash flag and its `task_*` channel) is expected to run it green.

The scenario's shape is fixed by a new acceptance criterion, tagged to the background-tasks capability:

> The claude-code e2e background-task scenario runs a wake-up matrix — {backgrounded bash, subagents} × {one-shot, streaming} — against a live model and asserts, in every cell, that task frames route to the right event family, that the run does not end at the first `result` but continues through the completion event and a continuation turn to `done`, that the control channel survives the held `result`, and that a healthy run emits no hold-bound `warning`.

Unpacked, that is four cells and four per-cell assertions:

| axis | values |
|------|--------|
| task source | backgrounded bash (`run_in_background`), subagents |
| input mode | one-shot, streaming |

Per cell, against a **live** model (not mocked):

1. Task frames route to the correct event family — `background_task_*`, derived from the SDK's `task_*` channel.
2. The run does **not** terminate at the first `result`; it continues through the task-completion event and a continuation turn to `done`.
3. The input/control channel is still usable across the held `result` — the session is not closed while work is in flight.
4. A healthy run emits **no** hold-bound `warning` (the bounded-hold warning is a failure signal, not routine noise).

This new criterion is declared to verify six pre-existing background-task criteria, i.e. this one scenario is the empirical proof for all of them:

- a `result` event is emitted while background work is still running,
- a `run_in_background` bash command settles after the turn,
- a task-touching run whose work has settled resumes correctly,
- `result.backgroundTasks` lists engine-backgrounded work,
- the claude-code adapter captures task type/identity from the SDK frames,
- the input/control channel stays open across the hold.

The consequence for the capability matrix is stated directly:

> The hold and the routing are proved live, not only by construction: claude-code's suite runs a wake-up matrix over {backgrounded bash, subagents} × {one-shot, streaming}, which is what makes the "control channel held with the session" row a measured ✅ rather than a design intent — coverage is owned by the adapter.

| `model matrix` (core scenarios × the model catalog) | ◻ planned | ◻ planned (unchanged) |

Two points are load-bearing here:

- **The MCP elicitation row is green with a caveat.** The scenario exists and runs, but it *self-skips* when the engine's MCP client refuses form elicitation. Reading it as unconditional proof of `elicitation_request` / `onElicitation` end-to-end would be wrong — on a host where the client refuses, the assertions never execute.
- **`error/resilience` was split.** It previously read `error/resilience (timeoutMs, out-of-range SDK → AdapterInitError)` and was `planned` as a unit. It is now two rows: `timeoutMs` is covered, and the SDK-version gate (an out-of-range SDK version must fail fast with `AdapterInitError`) is tracked separately and is **still not covered**. This is a deliberate un-bundling: the previous single row would have gone green while half of it stayed unwritten.

Scenarios already green before and after, unchanged: `simple-text`, `thinking`, `tool-use`, `subagents`, `plan-mode`, `todo`, `user-input`, `resume`, `abort`, `unknown-model`.

## For implementers

All work lands in the claude-code end-to-end suite; no adapter source change is required by this release.

1. **New scenario — `background-tasks`** in `src/testing/e2e/claude-code.e2e.test.ts`. Implement it as a 2×2 matrix, one test per cell:
   - task source: (a) a bash tool call issued with the SDK's `run_in_background` flag, (b) a subagent dispatch;
   - input mode: (a) one-shot (`prompt` string), (b) streaming input (`streamingInput` / `pushMessage`).
   In each cell assert, against a live model:
   - task frames surface as the `background_task_*` event family (sourced from the SDK's `task_*` frames), not as generic tool events;
   - the first `result` event is **not** terminal — the stream continues through the task-completion event and a continuation turn, and only then reaches `done`;
   - `pushMessage` (or the equivalent control-channel call) still succeeds while the run is held on the first `result`;
   - the run emits **no** hold-bound `warning` — assert its absence, do not merely ignore it.
2. **Fixture note:** a task's `tool_result` is not the same as its completion — the completion arrives on the task channel. Assert on the completion event, not on the tool result, or cells (a) will pass for the wrong reason.
3. **Skip guard:** the scenario must be adapter-gated. Codex, Gemini and OpenCode suites must skip it (their SDKs never background work) rather than fail; wire the skip through the same mechanism used for other unsupported-capability scenarios in `src/testing/e2e/`.
4. **Run it against the configured model** — the suite reads `E2E_CLAUDE_MODEL`; keep the new scenario inside the existing `test:e2e:claude:*` npm scripts in `package.json` so it is picked up by the standard e2e entry points rather than needing a bespoke command.
5. **Already-closed scenarios** — `image`, `mid-turn`, `path-scope`, `usage`, MCP elicitation, `timeoutMs`, and `os sandbox degrade` are recorded as covered in this release. If any of them is not actually present in `claude-code.e2e.test.ts` in your checkout, that is drift: the spec now claims coverage that the suite must provide. File it back rather than silently flipping the spec.
6. **Still open — `sdk-version gate`.** Not part of this release, but now tracked as its own row: a test that pins an out-of-range `@anthropic-ai/claude-agent-sdk` version and asserts the adapter throws `AdapterInitError` at init. Do not fold it back into `error/resilience`.
7. **MCP elicitation caveat** — if you touch that scenario, preserve its self-skip when the engine's MCP client refuses form elicitation; removing the skip will make the suite red on hosts where refusal is expected behaviour.
