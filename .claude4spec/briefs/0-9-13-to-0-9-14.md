# Brief: 0.9.13 → 0.9.14

This release fixes one gap, and every changed page is a different view of it. When a run reaches `result` but work is still unsettled, the claude-code adapter parks the run in a *control-channel hold* bounded by a hard cap (`claude_backgroundHoldCapMs`, default **90 s**). Until 0.9.14 that cap only listened to background tasks: a held **subagent** could be emitting `subagent_progress` — visibly working — and still be killed when the cap ran out, because nothing in the subagent's own lifecycle reset the timer. The cap now re-arms on the lifecycle events of *any* unit the hold tracks. No option, event, or error name changed; the cap simply stopped firing on work that was never actually stalled.

## The hold cap now listens to two event families

The cap is a silence timer armed at a held `result`. Before, its re-arm vocabulary was one family:

> re-armed by every `background_task_started` / `_progress` / `_completed` belonging to a task the adapter tracks

As of 0.9.14 it is two:

> re-armed by the lifecycle events of any unit the hold tracks — every `background_task_started` / `_progress` / `_completed` of a background task the adapter tracks, and every `subagent_started` / `subagent_progress` / `subagent_completed` of a subagent it tracks, a re-entry's `resumed: true` start included

The closed-vocabulary rule is unchanged and still load-bearing: the cap is **not** a heartbeat on the stream at large. Each event that re-arms it must belong to one named unit the hold is waiting on. Two families, one rule. Anything else crossing the stream — `system/status`, `system/background_tasks_changed` — still does not touch the cap.

At the adapter's event layer, the three SDK events `task_started` / `task_progress` / `task_notification` are routed by the `task_type` map into a tracked unit's family. Previously only a routing into `background_task_*` re-armed the cap; now a routing into either `background_task_*` **or** `subagent_*` does, "and by nothing else."

The cap remains a **single shared timer across all tracked units**, not one timer per unit. One tracked unit going quiet while another keeps reporting does not end the parked stretch — the timer is re-armed by whichever unit spoke last.

## What expiry still means

`AdapterBackgroundHoldExpiredError` is unchanged in name, shape, and teardown path: it is a runtime-phase error, it carries the cap value that was hit as a field, repeats it in the human-readable message, names the `architectureConfig` key that moves it, interrupts and aborts the session down the same path as `abort()`, and is the run's last event. Only its documented meaning widened — from "the engine's *background work* stalled and some of it was abandoned unfinished" to "the engine's *tracked work* — a background task or a held subagent — stalled and some of it was abandoned unfinished."

The two bounds on a parked run stay distinct and both keep their defaults:

- `architectureConfig.claude_backgroundGraceMs` — the **grace window**, re-armed by any frame arriving while parked (including `system/status` and `system/background_tasks_changed`). Its expiry ends the run silently at `result`.
- `architectureConfig.claude_backgroundHoldCapMs` — the **cap**, default 90 s, a silence-only timer over tracked work. Its expiry aborts with `AdapterBackgroundHoldExpiredError`. Non-numeric or non-positive values fall back to the default.

## Two caps now bound a subagent, and they bound different things

A subagent can be under two independent clocks, and 0.9.14 draws the line between them explicitly:

- `subagentTimeoutMs` bounds a subagent's total **length**. It re-arms on that subagent's own lifecycle events (`subagent_started`, a `resumed: true` restart, `subagent_progress`). Absent, no subagent carries a length cap.
- `claude_backgroundHoldCapMs` bounds that subagent's **silence** while it is parked in the post-`result` hold — not its length — on the same closed-vocabulary re-arm rule.

## New acceptance criteria

Three criteria were added, all tagged to the background-tasks module, all `status: active`:

1. *"A held subagent emitting subagent_progress re-arms the hold cap and is never cut short by it."* (`kind: requirement`) — the fix itself.
2. *"A parked stretch in which no subagent_* event arrives for a tracked held subagent ends at the cap with AdapterBackgroundHoldExpiredError."* (`kind: edge-case`) — the cap still fires on genuine silence; this is not a way to hold forever.
3. *"A parked stretch in which one tracked unit stays silent while another keeps reporting does not end at the cap."* (`kind: edge-case`) — pins the shared-timer semantics.

## Release classification

This ships **minor, with a mandatory CHANGELOG note naming the widened re-arm vocabulary**. Nothing is renamed, no signature moves, and a consumer that sets no new field sees a longer-lived run rather than a different API — but the behaviour is observably different: a held subagent that used to be cut at the cap while visibly working now runs on. A consumer that (deliberately or not) relied on the cap firing during active subagent progress will now see that run continue until the subagent genuinely goes silent for the full cap.

## For implementers

Concrete edit targets, ordered by dependency:

1. **The cap's re-arm predicate** — wherever the hold's timer is reset, the guard currently admits only the `background_task_*` family for a tracked task. Widen it to admit `subagent_started`, `subagent_progress`, and `subagent_completed` for a subagent the hold tracks, including the `resumed: true` start of a re-entry. Keep the membership test: the event must belong to a unit the hold is actually waiting on — do not relax this into "any frame re-arms the cap," which is the grace window's rule, not the cap's.
2. **Event routing** — the `task_type` map that dispatches the SDK's `task_started` / `task_progress` / `task_notification` into a unit family is the place where a `subagent_*` routing must reach the cap. If the cap subscribes downstream of this map, the change is a subscription widening, not new routing.
3. **Shared-timer invariant** — verify the cap is one timer for the whole hold, not per-unit. Criterion 3 above fails if a per-unit timer was introduced: a silent unit alongside a reporting one must not expire the stretch.
4. **`AdapterBackgroundHoldExpiredError`** — no code change to the class. Only message/doc copy referring to "background work" should read "tracked work". The field carrying the hit cap value and the `architectureConfig` key it names stay as-is.
5. **Tests** — three new cases matching the criteria above: (a) a held subagent emitting `subagent_progress` past the cap duration survives; (b) a tracked held subagent emitting nothing for the full cap terminates with `AdapterBackgroundHoldExpiredError`; (c) two tracked units, one silent past the cap and one reporting, and the run continues.
6. **CHANGELOG** — a minor entry naming the widened vocabulary explicitly, e.g. "the background hold cap now re-arms on `subagent_started` / `subagent_progress` / `subagent_completed` of a tracked held subagent, in addition to `background_task_*` events."

Config keys, defaults, event names, error classes, and public signatures are untouched by this release — there is nothing to migrate.
