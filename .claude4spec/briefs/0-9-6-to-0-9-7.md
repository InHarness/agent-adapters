# Brief: 0.9.6 → 0.9.7

`0.9.7` closes the contract that `0.9.6`'s tool-gating work left half-open: **what exactly a delegated subagent inherits from the run that spawned it.** Before this release the library shipped subagents (definitions, lifecycle events, `subagentTaskId`) without an answer to "can a subagent reach a file, a tool, an MCP server, or a model that its parent could not?" — the answer was implied by adapter code but never stated, never tested, and therefore not something a consumer could rely on.

The release answers it with one invariant — **a subagent's reach equals the run's** — and then works out what that means field by field. The subagent definition is now a formally specified nine-field envelope with three explicit inheritance tiers; filesystem path-scope and tool deny-groups are pinned as un-overridable; model resolution, MCP config and skills each get a stated rule; a new capability row says which adapters accept a definition at all; and the e2e suite grows a leg that proves the filesystem rule against a live model instead of asserting it from construction.

There are no new public types or endpoints. What changed is that a set of behaviours that were previously accidental are now contract, with the failure modes enumerated.

## The subagent definition envelope

`SubagentDefinition` is now specified as a deliberately reduced, adapter-agnostic envelope of exactly nine fields. Anything the underlying SDK offers beyond these is withheld on purpose (see "Deliberately not exported" below).

| field | required | when omitted | guarantee |
| --- | :---: | --- | --- |
| `name` | yes | — | the agent type the model invokes; must be unique within a call |
| `description` | yes | — | *when* to delegate here; the model reads it to route |
| `prompt` | yes | — | the subagent's **own** system prompt |
| `tools` | no | inherits the parent's tools — under a tool-gating policy, the run's **residual** allow-list | allow-list, then intersected with the run's deny-groups |
| `disallowedTools` | no | under a policy, the run's denies; with **no** policy, nothing — a subagent does not natively inherit parent denies | unioned with the run's denied built-ins |
| `model` | no | inherits the main model | passed to the SDK **verbatim**; not re-resolved through the model catalog |
| `skills` | no | none preloaded | names, not bodies — delivery stays with the skills module |
| `maxTurns` | no | SDK default | bound on agentic round-trips |
| `effort` | no | SDK default | named levels only; the SDK's integer form is not exposed |

Two semantics are now stated explicitly because they were previously guessable both ways:

- **`prompt` replaces the parent's system prompt — it never extends or concatenates it.** A subagent starts from its own instructions, not the parent's plus a suffix.
- **`tools` narrows only, never widens.** A subagent's tool set is *derived* from the run's effective policy, not independent of it. Naming a tool the run does not hold does not hand it back.

## Three inheritance tiers

The envelope's fields are grouped by how much vote the definition has over what it inherits:

1. **Fresh per subagent** — system prompt, conversation, turn budget. The definition has total vote (`prompt` replaces outright).
2. **Inherited unless narrowed** — toolset, MCP servers, model. The definition may narrow; it may never widen.
3. **Inherited unconditionally, no vote at all** — filesystem path-scope and tool deny-groups. *No field of the envelope expresses either.*

Tier 3 is the load-bearing one, and its two members get there by different machinery — the release is explicit that this asymmetry is by construction, not an inconsistency:

- **Deny-groups need active propagation.** On claude-code a spawned subagent does **not** inherit the parent's tool denies. Without propagation, "deny the shell" means "deny the shell until the model delegates" — which is not a boundary at all. So the adapter resolves the run's deny-groups against each subagent's own toolset and applies them to every definition, including definitions a consumer wrote without knowing tool gating existed. Propagation is what lets the tool-gating module report a strength above `none` for that group.
- **Path-scope needs no propagation.** The envelope has no field that could express a scope, and the one SDK field that could re-open one — `AgentDefinition.permissionMode` — is deliberately never set by this library.

The invariant is phrased carefully: **"a subagent's reach equals the run's"**, *not* "a subagent is confined". On a run that declares neither `allowedPaths` nor `disallowedPaths` there is no ceiling to inherit (the claude-code session keeps `bypassPermissions`), so tier 3 is vacuous there rather than violated.

## Path-scope inherits, and its strength inherits with it

The path-scoping module now states that the declared scope binds every agent in the run, spawned helpers included. A subagent may hold a *different* toolset than its parent — specialization is fine — but may never reach a path the parent run cannot reach.

The two enforcement paths hold this by different machinery:

- **Hard path** — an OS sandbox confines the whole process at syscall level, so a spawned helper cannot be outside it.
- **Soft path** — confinement rides the session's permission rules, which the claude-code SDK scopes to the *session*, not per-agent, plus the guarantee that `AgentDefinition.permissionMode` is never set.

> Inheritance transfers the boundary, not its strength: a subagent under a soft scope inherits a *soft* scope, with every caveat `soft` already carries.

The soft path ships with an explicit **⚠️ verification-pending marker**: it is asserted from adapter construction but was not yet measured against a live model at the time of this release. The marker comes off when the new e2e leg (below) is green. Consumers are told to know which of the two paths they are relying on, "because only one of them is a sandbox".

New edge case, spelled out:

> A run under soft path-scope delegates to a subagent whose definition names `Read` → the subagent's read is evaluated against the same allow/deny rules as the parent's, so a path outside `cwd ∪ allowedPaths` is refused for the subagent exactly as it is for the parent.

## Model, MCP and skills — three cross-module rules pinned

Four new relation lines were added to the architecture index, each formalising a contract that was previously unstated:

```
M06 Subagents ── passes model through ──> M02 Models (a subagent's model is not resolved against the catalog)
M06 Subagents ── inherits servers from ──> M04 MCP (no per-subagent MCP config; filtered by the subagent's toolset)
M06 Subagents ── names skills from ──> M05 Skills (delivery and discovery stay M05's)
M06 Subagents ── inherits scope from ──> M15 Path-scope (a subagent's reach equals the run's)
```

**Model resolution is bypassed by design.** A definition's `model` reaches the SDK unresolved — it is *not* run through the unified model catalog (aliases, resolved ids, context windows). The consequence is stated as an edge case: a definition setting `model` to a unified alias the catalog knows but the SDK does not is passed through unchanged and **rejected SDK-side**.

**A subagent carries no MCP configuration of its own.** It sees the run's servers narrowed by its own toolset. Practically:

> An `mcp__server__*` entry in a `SubagentDefinition`'s `disallowedTools` is the only per-subagent MCP control there is.

Withholding a server from one subagent is therefore a *toolset* decision, not a deny-group decision — tool gating still covers built-ins only, and does not extend to MCP tools even at subagent level.

**`skills` names skills, it does not deliver them.** If a definition names a skill the skills module did not deliver for this adapter, the subagent starts anyway and the skill is simply not there — no error.

## New capability row: is the definition accepted at all?

The subagent support matrix gained a row above the existing lifecycle rows. Consumer-defined subagents are a claude-code-family capability; everywhere else the definition is accepted syntactically and then ignored with a warning.

| Behavior | claude-code | codex | gemini | opencode |
| --- | :---: | :---: | :---: | :---: |
| **Definition accepted (`subagentDefinition`)** | ✅ definitions become native agent types | ⚠️ warn-and-ignore | ⚠️ warn-and-ignore | ⚠️ warn-and-ignore |
| Lifecycle events | ✅ native `task_*` | ⚠️ synthesized | ⚠️ synthesized per `threadId` | ⚠️ synthesized |
| `subagentTaskId` on deltas | ✅ from `parent_tool_use_id` | ❌ no subagent concept | ✅ pass-through `event.threadId` | ⚠️ ordering-based (single active) |

A clarifying note was added: the `claude-code` column stands for the whole `claude-code-*` family — `claude-code-ollama` and `claude-code-minimax` report `subagentDefinition` true as well. The four columns are **families, not an exhaustive list of registered architecture ids**.

## Adapter wiring (claude-code)

The claude-code adapter's per-capability consumption notes were expanded from a one-liner to the actual mapping onto `Options.agents`:

- `name` becomes the **key** of `Options.agents` — the SDK's `AgentDefinition` has no name field of its own.
- `tools` / `disallowedTools` pass through the subagent tool-policy function. **When a tool policy is in play the subagent's `tools` is always pinned** — either to the filtered list, or, if the definition omitted the field, to the run's full residual allow-list. When there is no policy, neither `tools` nor `disallowedTools` is sent at all and the SDK's own inheritance applies (which, for denies, is *no* inheritance).
- `model`, `skills`, `maxTurns`, `effort` map 1:1; an unset field is **omitted from the SDK object entirely** rather than sent as explicit `null`, so the SDK default applies.

## Deliberately not exported

The public-API section now enumerates the SDK capabilities the envelope withholds, each framed as "a contract change to add, not a backlog item":

- **`permissionMode`** — the SDK's only per-agent override of the session permission posture. Exporting it would let a definition set itself back to `bypassPermissions` and out of the run's path-scope. This is the field the whole soft-path guarantee rests on.
- **`background`** — a fire-and-forget agent is exactly the shape the scope rule separates from itself; exposing it would land a subagent in the background-tasks lifecycle.
- **`mcpServers`** — per-subagent MCP would be a second, adapter-specific MCP surface next to the unified one; inheritance plus toolset filtering covers the observed need.
- **`memory`, `initialPrompt`, `observer` / `observerMessage`, `criticalSystemReminder_EXPERIMENTAL`** — claude-code-only constructs with no analogue on the other three adapters; carrying them would make the envelope untranslatable and would put an `_EXPERIMENTAL` field under the semver promise.

## Validation and failure modes

`validateSubagents` requires a non-empty `name`, `description` and `prompt` on every definition, and requires **unique names within the call**. It throws **before the run**, not mid-stream — a malformed set is a definition-time error, not a streaming failure.

New or newly-explicit edge cases:

- Two definitions in one call share a `name` → `validateSubagents` throws before the run; **neither** is registered.
- Definition omits `tools` on a run with deny-groups → the subagent inherits the run's **residual allow-list**, not the SDK's full default toolset.
- Definition sets `model` to a unified alias the catalog knows but the SDK does not → passed through unchanged, rejected SDK-side.
- Definition names a skill the skills module did not deliver for this adapter → the subagent starts anyway; the skill is simply absent.
- Definition supplies a `tools` allow-list naming `Bash` on a run under soft path-scope → **the subagent does not get it.** The default-deny posture pre-approves the file built-ins only, so shell and web are withheld from parent and subagent alike, and an allow-list cannot hand back what the run never held.

## Test coverage: one honest downgrade, one new leg

The e2e `subagents` scenario gained an assertion. It previously proved only that delegated work emits `subagent_*` lifecycle with a consistent `subagentTaskId`, and that a consumer-defined subagent is invocable. It now additionally proves:

> a subagent inherits the run's filesystem ceiling — under a soft path-scope, a subagent asked to read outside `cwd ∪ allowedPaths` is refused exactly as the parent would be.

Correspondingly the claude-code adapter's e2e coverage table **downgraded** its own row, rather than claiming coverage it did not have:

| before | after |
| --- | --- |
| `subagents` (+ consumer-defined subagent) — ✅ covered | `subagents` (+ consumer-defined subagent) — ⚠️ partial — lifecycle and the consumer-defined subagent are covered; the soft path-scope leg (a subagent asked to read outside the run's ceiling is refused) is not implemented yet |

Five new acceptance criteria back the contract above (four requirements, one edge-case):

1. A subagent's prompt replaces the parent run's system prompt rather than extending it.
2. A subagent definition that omits `tools` inherits the run's residual allow-list, not the SDK's full default toolset.
3. A subagent definition's `model` reaches the SDK unresolved, because subagent models bypass the model catalog by design.
4. A subagent's filesystem reach equals the run's declared path-scope; no field of the subagent envelope can narrow or widen it.
5. *(edge-case)* A subagent definition's `tools` allow-list naming a tool the run's path-scope posture withholds does not restore that tool.

A sixth criterion covers the live proof: *the claude-code e2e `subagents` scenario proves against a live model that a subagent of a soft path-scoped run is refused a read outside `cwd ∪ allowedPaths`* — and it explicitly verifies criterion (4) above.

## Unrelated: the background-tasks success assertion was tightened

One pre-existing criterion outside the subagent thread changed. The claude-code e2e background-tasks scenario's definition of a *silent* healthy run was reworked:

- **Before** — a healthy run ends silently: no hold-bound `warning` and no `AdapterBackgroundHoldExpiredError` on a run whose work settled.
- **After** — a healthy run ends silently: **the hold cap is never hit** — no `AdapterBackgroundHoldExpiredError` and **no terminal `error` event, the run's last event being its `result`** — with the absence of any hold-bound `warning` kept beside it only as a regression guard against the warning-and-carry-on shape this bound replaced.

The assertion's centre of gravity moves from "no warning was emitted" to "the run terminated on `result`, never on `error`". The warning check survives only as a guard against regressing to the older warning-and-carry-on behaviour.
