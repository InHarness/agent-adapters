# Brief: 0.9.9 → 0.9.10

This release closes two holes where the library reported success it could not
back up. First: a subagent that was still running when a run was terminated
(`abort()`, `timeoutMs`, or hold-cap expiry) simply stopped emitting events — a
consumer bucketing deltas by `subagentTaskId` had no way to tell "finished" from
"killed with the run", so the bucket never closed. The adapter now synthesizes
the closing event, and `subagent_completed.status` gains a closed vocabulary plus
a shared mapper so an unknown SDK terminal reason can never be silently
reinterpreted as success. Second: the Claude Code adapter's dev-pin floor was
raised after the discovery that `@anthropic-ai/claude-agent-sdk` bundles a CLI
executable which validates model ids itself — an in-range but too-old SDK
resolves a new alias fine and then fails at request time with a 400.

## Subagent lifecycle: every `subagent_started` gets exactly one close

`subagent_completed.status` is now a closed vocabulary:

```ts
type SubagentStatus = 'completed' | 'failed' | 'aborted' | 'stopped';
```

An adapter must map its own SDK's terminal reason onto that vocabulary rather
than pass the raw value through. The mapping is owned by one shared function:

```ts
mapSubagentStatus(raw, declared): SubagentStatus
```

The binding rule: **a terminal reason outside the known vocabulary never
resolves to `'completed'`** — `mapSubagentStatus` falls back to the caller's
`declared` value instead. The failure this prevents is undetectable downstream:
a subagent that actually died reported as successful looks identical to one that
succeeded.

Termination now closes what it interrupts. When `abort()`, `timeoutMs` expiry or
hold-cap expiry ends the run while a subagent is still open, the adapter
synthesizes a closing event for **every unpaired `subagent_started`**:

```ts
subagent_completed { status: 'aborted' }
```

Two constraints bound this:

- **At most once per `taskId`.** A subagent that already emitted its own terminal
  event is not closed a second time. No `subagent_started` may ever be followed
  by more than one `subagent_completed`, including on the synthesis path.
- **This is deliberately the opposite of background tasks.** After termination no
  `background_task_completed` is owed — background work is designed to outlive the
  turn, so silence there is legible. A subagent is a bracket *inside* the turn:
  an unpaired `subagent_started` against a dead run is indistinguishable from one
  still in flight, which is why the close is synthesized here and not there.

### Tool-deny propagation into subagents

Run-level deny-groups are now resolved against a subagent's own toolset and
applied to **every** subagent definition the run spawns — including definitions
the consumer authored without knowing tool gating exists. The reason is
adapter-specific and load-bearing: on `claude-code` a subagent does **not**
inherit the parent's tool denies, so without propagation a run-level "deny the
shell" holds only until the model delegates. Propagation is what allows the
gating layer to report a deny strength above `none` for such a group.

### New public exports (under the semver promise)

The package root previously exported `SubagentDefinition` and
`validateSubagents`. It now exports:

| export | kind | meaning |
|---|---|---|
| `SubagentDefinition` | type | unchanged |
| `SubagentStatus` | type | `'completed' \| 'failed' \| 'aborted' \| 'stopped'` |
| `validateSubagents` | function | unchanged |
| `mapSubagentStatus` | function | `(raw, declared) => SubagentStatus` |

`SubagentStatus` and `mapSubagentStatus` are new API surface and are covered by
the semver promise — consumers may rely on them.

## Claude Code: the bundled CLI, not the SDK, decides which models work

`@anthropic-ai/claude-agent-sdk` ships a Claude Code CLI executable inside its
tarball, and that executable — not the SDK's TypeScript surface — validates model
ids before the request leaves the machine. The version relation was verified by
unpacking the `0.3.220`, `0.3.251` and `0.3.263` tarballs:

```
SDK 0.3.N  bundles  Claude Code CLI 2.1.N
```

A rejection therefore surfaces at **request time**, not as an init fault:

```
API Error: 400 Claude Code 2.1.220 does not support this model;
version 2.1.251 or newer is required
```

Concretely: the alias `claude-fable-5-1` requires CLI ≥ `2.1.251`, hence SDK ≥
`0.3.251`. The adapter's dev-pin floor moves accordingly:

| | before | after |
|---|---|---|
| dev-pin | `^0.3.210` | `^0.3.251` |
| rationale | "consumers already run 0.3.210 in production" | below this floor the bundled CLI refuses the newest resolved ids in the model catalog |

Latest published `0.3.x` at the time of writing is `0.3.263`.

The consequence for consumers: the model catalog is canon over model **ids**, but
not over their reachability on every in-range SDK. A consumer sitting on an
in-range but sub-floor `0.3.x` will resolve the alias without error and still get
a 400 from the engine.

Two caveats are recorded rather than resolved:

- Only one floor is known — the one for `claude-fable-5-1`. The older 1M aliases
  (`claude-fable-5`, `claude-sonnet-5`, `claude-opus-5`) are *assumed* to sit
  below CLI `2.1.251` on field evidence (no reported 400s), not on an actual
  probe.
- The `0.3.210` pin's full `test:e2e:claude:*` run never happened; that row is
  marked `abandoned (superseded by ^0.3.251)`. Its probe results
  (`background_tasks` behaviour, wake-up gap timings) still stand as measured.
  The new `^0.3.251` row is backed by targeted evidence only and remains
  `pending verification`.

### Maintenance rule this creates

Adding or changing an alias in the model catalog now also obliges a re-check of
the affected adapter's dev-pin floor, so the resolved id stays *reachable* and
not merely *declared*. This applies to any adapter whose peer SDK bundles an
executable runtime; today that is `claude-code`.

## Conformance: the abort e2e scenario grew a subagent leg

The `abort` scenario in the e2e catalog previously asserted only that `abort()`
mid-stream ends the run cleanly (`AdapterAbortError`, channel closed). It now
additionally asserts that a subagent caught in flight is closed rather than
abandoned: every unpaired `subagent_started` receives its
`subagent_completed { status: 'aborted' }`, at most once per `taskId`. The
scenario runs against a live model, with subagents genuinely in flight at the
moment abort fires.

## For implementers

1. Add the status type and mapper in the subagents module's contract types
   (e.g. `src/subagents/types.ts`):
   ```ts
   export type SubagentStatus = 'completed' | 'failed' | 'aborted' | 'stopped';
   export function mapSubagentStatus(raw: string, declared: SubagentStatus): SubagentStatus;
   ```
   The fallback branch must return `declared` for any `raw` outside the four
   literals — never `'completed'`.
2. Re-export both from the package root (`src/index.ts`), alongside the existing
   `SubagentDefinition` and `validateSubagents`. These are semver-covered.
3. Route every adapter's subagent terminal event through `mapSubagentStatus`
   instead of assigning `status` directly from the SDK payload.
4. Track open subagents per run: keep a set of `taskId`s that emitted
   `subagent_started` and remove each on its natural `subagent_completed`.
5. On the run-termination paths (`abort()`, `timeoutMs` expiry, hold-cap expiry),
   drain that set and emit one synthetic
   `subagent_completed { status: 'aborted' }` per remaining `taskId`, then clear
   it. Guard with the set membership so a subagent that already closed is never
   closed twice. Do **not** apply the analogous treatment to background tasks —
   no `background_task_completed` is owed after termination.
6. In the tool-gating path, resolve run-level deny-groups against each subagent's
   own toolset and inject them into every spawned subagent definition (needed
   because `claude-code` subagents do not inherit parent denies). Update the
   reported deny strength for such groups from `none` accordingly.
7. Bump the claude-code dev dependency floor from `^0.3.210` to `^0.3.251` in
   `package.json` (expected resolved pin: `0.3.263`). Record the exact resolved
   pin in the verified-pin log once the full `test:e2e:claude:*` suite has run
   across the model scripts.
8. Extend the `abort` e2e scenario so it spawns subagents and aborts mid-stream
   while at least one is in flight; assert one `subagent_completed` per
   `subagent_started`, `status === 'aborted'`, and no duplicates per `taskId`.
9. While running (8) across the model scripts, probe whether `claude-fable-5`,
   `claude-sonnet-5` and `claude-opus-5` are in fact accepted below CLI
   `2.1.251` — the current assumption that they are is untested.
