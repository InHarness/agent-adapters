# Brief: 0.9.3 → 0.9.4

## Summary

This release introduces **peer-SDK pin governance**: every adapter/module that wraps a third-party SDK must now carry a *Verified-pin log* — an append-only table recording which dev-pin was actually verified, by what, and what it found — and dev-pin bumps become a **spec-first workflow** (spec edit → release brief → `devDependencies` + full e2e → findings written back).

The concrete payload for implementers: the `claude-code` peer-SDK dev-pin policy changed from a fixed `^0.3.153` to a **floor of `^0.3.210`, targeting the latest `0.3.x`**, with a log row already sitting in the spec marked `pending verification` that this implementation must complete.

## What changed

### 1. New required field in every SDK-compatibility section — Verified-pin log

`spec/layers/L7-sdk-compatibility.md` ("Module slice schema") adds a bullet that every L7 consumer section must now answer:

> **Verified-pin log** — a table `| date | dev-pin | verified by | findings |` recording every dev-pin this consumer has *actually* been verified against (an e2e run, or documented live use), newest row last.

Three rules ride on the field:

- The **newest row's dev-pin must equal** the pin named in the section's *Supported peer-SDK range* bullet. The two move in the same edit, so the pin has exactly one home and the log never lags it.
- Findings are recorded **honestly** — `none observed` is a valid finding, an invented one is not.
- Rows are **append-only**. A row may be written *ahead* of its verification with `findings: pending verification` when the bump is specified spec-first, and is completed once the suite has run.

### 2. Spec-first peer-SDK bump workflow

`spec/modules/M12-conformance-release.md`, section "Public API & Packaging (L4)", replaces its old tail bullets with the governing process rule:

> **Peer-SDK bump workflow (spec-first).** A dev-pin bump is edited **in the spec before it is edited in `devDependencies`** — the same canon rule the M02 model catalog follows. Order: (1) the consumer's L7 section changes first — the pin named in *Supported peer-SDK range* plus a new Verified-pin-log row carrying `findings: pending verification`; (2) a release brief carries that bump to the implementer; (3) the implementer updates `devDependencies`, runs the **full** e2e suite for that consumer (`test:e2e:<adapter>`, × model scripts where parametrized), and writes the result — including "none observed" — back into the pending row via patch-feedback. A bump whose row is never completed is an unfinished bump, not a passing one.

Explicitly **no multi-version test matrix**: exactly one verified pin per consumer at a time.

### 3. claude-code dev-pin: fixed number → moving floor

`spec/adapters/A01-claude-code.md` drops the static `dev-pinned ^0.3.153` and replaces it with:

> The **dev-pin** inside that range is a separate, faster-moving decision: the target is the *latest 0.3.x at brief time, minimum `^0.3.210`* — consumers already run 0.3.210 in production, so verifying against a pin two dozen patches behind them measures the wrong SDK. The exact pin is the implementer's resolution at bump time; what is canon here is the floor and the log below.

Its Verified-pin log carries two rows:

### 5. New acceptance criteria (M12)

Both `kind: requirement`, `status: active`, `tags: ["m12"]`:

1. **"A peer-SDK dev-pin bump appears in the spec — the L7 pin plus a Verified-pin-log row — before the matching `devDependencies` change ships in a release brief."**
   Observable on any bump: the release brief carrying the `devDependencies` change cites an already-edited L7 section whose new log row reads `pending verification`. A brief that bumps the pin without a preceding spec edit fails; so does a shipped bump whose pending row was never completed with the e2e findings.
2. **"Every L7 consumer section contains a Verified-pin log whose newest row names the same dev-pin as its Supported peer-SDK range."**
   Checked by reading each L7 consumer section (A01–A04, M04): the log table exists and its last row's dev-pin string is identical to the pin named in the *Supported peer-SDK range* bullet. A log lagging its range means the pin has two homes again — the drift this field exists to prevent.

## For implementers

Only one item in this release produces a code change; the rest is spec governance that constrains *how* future bumps are done.

1. **Bump the `@anthropic-ai/claude-code` (claude-code SDK) dev-pin.**
   - File: `package.json` → `devDependencies`.
   - Resolve the **latest published `0.3.x`**, but not below `0.3.210`. Record the exact resolved version.
   - Do **not** widen the supported peer range — only the dev-pin moves.

2. **Run the full claude-code e2e suite against the new pin** — `test:e2e:claude:*` (all scripts, including the per-model parametrized ones). Targeted probes are not sufficient; the AC treats a pin verified only by probes as unfinished.

3. **Expect / re-verify these behavioural deltas vs `0.3.153`** (they were observed in probes and are why the floor moved). Any code that special-cased the 0.3.153 behaviour should be revisited:
   - `StopHookInput.background_tasks` now lists subagents; on 0.3.153 it returned `[]` (and could be absent entirely). Code that treated an empty/absent list as "no background work" may now see entries.
   - `BackgroundTaskSummary.type` can read `'subagent'` as a display label — alongside the already-known `local_bash` spelling for `task_type`.
   - Post-settle wake-up gap drops from ~5.0 s to ~3.5–3.7 s with partials. Any hard-coded settle/timeout constants tuned to 5 s should be checked.

4. **Write the findings back into the spec's pending row** (via patch-feedback on this brief, not by editing `spec/` directly if you are the implementer): complete `spec/adapters/A01-claude-code.md`'s Verified-pin log row with the run date, the exact resolved pin, and the findings — `none observed` if the suite was clean. Leaving the row at `pending verification` means the bump is not done.

5. **No other dependency changes.** codex `^0.120.0`, opencode `^1.4.6`, gemini `^0.38.0`, MCP SDK `^1.29.0` stay exactly as they are — their spec entries are log seeds, not bumps. Do not introduce a multi-version test matrix.
