# Brief: 0.9.0 → 0.9.1

## TL;DR

This release adds **engine-backgrounded task support** to the unified layer. When a Claude Code run spawns a `run_in_background` Bash command (or a monitor/workflow task), the agent turn's `result` arrives *before* that shell work finishes. Previously such work was folded into the `subagent_*` channel and consumers that stopped iterating at the first `result` silently missed the completion and timed out. Now:

- A new **`background_task_*`** UnifiedEvent family reports that lifecycle separately from real subagents.
- A new **`result.backgroundTasks`** in-flight signal tells consumers a `result` is *not* terminal — they must keep iterating `execute()` until the generator is `done`.
- The claude-code adapter routes the shared SDK task channel by `task_type`, keeps its control channel open while background work is in flight, and drives **every** run (even one-shot string prompts) through a seeded input channel so a woken model can still ask questions.

Plus catalog work: a new **`opus-5`** model (`claude-opus-5`, 1M context, adaptive-thinking-only), and two behavioral-contract clarifications in the mid-turn-input (M11) and errors/resilience (M13) modules.

Only the **claude-code** adapter implements background tasks; codex, gemini, and opencode simply never emit the new family (graceful absence, not an error).

## 1. New UnifiedEvent family: `background_task_*`

Three new event types are added to the unified event taxonomy (type home: the M01 unified-event layer, mirrored in `src/types.ts`):

```
background_task_started    { taskId, taskType, description }
background_task_progress   { taskId, taskType, status?, outputFile? }
background_task_completed   { taskId, taskType, status, outputFile?, summary?, usage? }
```

- `taskType` is a discriminator with values `'shell'` (backgrounded shell command, e.g. `run_in_background` Bash), `'monitor'` (a watch/monitor task), and `'workflow'` (an orchestration run). Real subagents stay on the existing `subagent_started/progress/completed` channel.
- `outputFile` is a **tail target** — a file path into which the engine streams the backgrounded process's stdout. The unified stream carries lifecycle events only, not the process stdout itself; consumers tail `outputFile` for live output.

### New `result.backgroundTasks` in-flight signal

The `result` event gains a `backgroundTasks` field (owned by M01). A **non-empty** value means the run is NOT over even though a `result` has arrived: the engine keeps the session open, and `execute()` will subsequently yield the `background_task_completed`, a continuation turn, and a *further* `result` before the generator ends.

**Blessed consumer contract (the one rule that prevents the classic timeout bug): read the stream to `done`, not to the first `result`.** No watcher, polling, or backoff is required in consumer code — the engine wakes the model on task settlement (a "push resume" model). A "pull model" using session resume (M07) with consumer-side backoff polling is explicitly documented as out-of-scope and NOT standardized.

### Degradation

On adapters whose SDK never backgrounds work (codex, gemini, opencode), no `background_task_*` event is ever emitted and `result` never carries a `backgroundTasks` signal. This is an **absence, not an error or warning** — the standard skip-strategy degradation.

## 2. claude-code adapter (A01): routing, in-flight tracking, channel hold

### 2a. Route the shared SDK task channel by `task_type`

The Claude Code SDK multiplexes both subagents and background shell work onto the same `system` messages: `task_started` / `task_progress` / `task_notification`. The discriminator lives ONLY on the start message:

- `SDKTaskStartedMessage` carries `task_type?` (plus `subagent_type?` / `workflow_name?`).
- The follow-up `task_progress` / `task_notification` messages carry only `task_id`, `status`, `output_file`, `summary`, `usage` — **no `task_type`**.

Required adapter behavior: on `task_started`, capture `task_type` into a **`Map<task_id, task_type>`**, then route every later message for that `task_id` through the map:

- `task_type ∈ { 'shell', 'monitor', 'workflow' }` → `background_task_started/progress/completed` (M17).
- subagent kinds → `subagent_started/progress/completed` (existing).
- **unknown or absent `task_type` → defaults to the subagent path** (preserves legacy behavior).

A `run_in_background` Bash command's settlement therefore surfaces as `background_task_completed` carrying the `taskId` from its `background_task_started`, the settlement `status`, and the `outputFile` tail target — **never** as `subagent_completed`.

### 2b. Track in-flight background tasks adapter-side

The SDK does **not** expose an in-flight list on `result`: `SDKResultMessage` has no `background_tasks`; the SDK only surfaces `background_tasks[]` on `StopHookInput` / `SubagentStopHookInput`. So the adapter must maintain its own set — a task is in-flight from `task_started` until its `task_notification`. This tracked set (a) drives the control-channel hold below and (b) populates M01's `result.backgroundTasks` signal (background kinds only). If a future SDK adds `background_tasks[]` to `result`, treat it as a **union** with the tracked set, never a replacement.

### 2c. Hold the control channel open while work is in flight

While in-flight background work exists, the adapter MUST keep its input/control channel to the engine open. The CLI is spawned with `--permission-prompt-tool stdio`, so the control protocol (permission prompts, user-input requests, hook callbacks) shares **stdin** with prompt input. Closing stdin at `result` kills the control transport even though the run loop keeps running: a woken model's `AskUserQuestion` is then **denied locally within milliseconds inside the CLI** — no host round-trip, no stream error. Failure signature if you get this wrong: a `tool_result` reading `Tool permission request failed: … Stream closed`, the model retries then asks in prose, and no `user_input_request` ever reaches the stream.

The adapter closes the channel on the continuation `result` once the tracked set drains.

**The hold is double-bounded** (must still terminate if work never settles):
1. a short **grace window** after the last task settles — the continuation turn must begin within it; and
2. a hard **cap** on total hold time measured from the first held `result`.

On either expiry the adapter closes the channel, ends the run, and emits a `warning` naming the bound. Both bounds degrade to pre-hold behavior (run ends at `result`).

### 2d. Every run now uses the seeded input channel

Even a one-shot plain string prompt is now driven through a seeded streaming input channel. Reason: the Claude Code SDK marks a string prompt as a single-turn query and calls `transport.endInput()` at the first `result`, closing the CLI stdin (same control-transport-death problem, done by the SDK where the adapter cannot intervene). Consequences:

- `streamingInput` now only gates `pushMessage()` — it no longer implies a particular wire shape.
- `Query.interrupt()` is now available on **every** run (previously only on streaming runs), so `abort()` teardown works universally.

### 2e. Disable lever: `claude_disallowBackgroundBash`

New config key **`architectureConfig.claude_disallowBackgroundBash: true`** (L3 adapter-prefixed key, default `false`/off). There is no SDK option to forbid backgrounding, so the lever is implemented as a **synthesized `PreToolUse` deny-hook** that rejects Bash calls requesting `run_in_background: true`. With it on, such a call is denied and the command runs **synchronously inside the turn** — no `background_task_*` events, and `result` carries no in-flight signal.

### 2f. Unrealized SDK controls (documented, NOT consumed)

`Query.stopTask()`, `Query.backgroundTasks()`, and the `is_backgrounded` flag are intentionally not used yet. Per-task stop and mid-run enumeration remain unrealized; `abort()` stays a coarse whole-run stop bounded by M13.

## 4. Contract clarifications

### M11 (mid-turn input): `streamingInput` gates pushes, not the channel

`streamingInput: false` no longer implies a particular wire-level implementation (a string prompt). What it guarantees is the *consumer-facing* contract only: `pushMessage()` returns `false`, and the stream yields exactly one `result`. An adapter may still drive its SDK through an input channel on every run — a one-shot run is then a channel seeded with the prompt and closed at the turn's `result`, observationally identical to a string prompt. Adapters do this when the SDK's one-shot path is degraded (see A01 §2d).

### M13 (errors/resilience): `abort()` / `timeoutMs` must break a pending user-input await

New rule (general, not A01-specific): when `abort()` or `timeoutMs` fires while a `user_input_request` is unanswered, the run MUST still terminate. A consumer's `onUserInput` handler routinely resolves only when a human answers (HTTP round-trip, UI dialog) — possibly never. An adapter that simply awaits it parks the run forever, holding its session *and* its SDK subprocess (a wedge that is invisible in logs and appears to "heal on restart"). Adapters MUST race the abort signal against every consumer handler they await: on abort, the outstanding request is answered `cancel` (so the SDK-side promise settles instead of leaking), the stream yields `AdapterAbortError` / `AdapterTimeoutError`, and teardown runs.

Interaction with background tasks: when `abort()` or `timeoutMs` fires with background work in flight, the run terminates per M13 and **no `background_task_completed` is emitted after termination**.
