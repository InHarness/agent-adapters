# Brief: 0.9.5 → 0.9.6

This release gives a consumer a way to **amputate whole classes of built-in tool capability from a single run** — shell, filesystem reads, filesystem writes, web — declared once in engine-neutral terms and realized by each adapter with its own SDK primitive. It arrives as a new capability-module, **M18 "Built-in tool gating (deny-groups)"**, and it is deliberately **fail-closed**: when an adapter has no primitive for a requested group, the run is refused *before dispatch* instead of running with a hole in it. `planMode: true` stops being a per-adapter improvisation and becomes a preset that desugars into deny-groups, which means plan mode now refuses on adapters that cannot enforce it (previously: a `console.warn` and a silently unenforced run).

Two smaller but breaking things ride along: the run param `allowedTools` is **renamed to `autoApproveTools`** (it never restricted anything — three of four adapters ignored it), and the M17 background-task control-channel hold now ends an over-cap run with a **terminal typed error** instead of a `warning` that left a half-dead session alive.

This is a **major** release. The trigger is the `allowedTools` → `autoApproveTools` rename; the plan-mode behavioural hardening rides that same bump and must be named explicitly in the CHANGELOG together with its opt-out (an explicit empty `disallowedToolGroups`).

---

## 1. New run params

Two additions on `RuntimeExecuteParams` (type home: M01 unified core):

```ts
type ToolGroup = 'shell' | 'file-read' | 'file-write' | 'web'

interface RuntimeExecuteParams {
  // ...existing fields
  /** Classes of built-in tool capability this run may not use. */
  disallowedToolGroups?: ToolGroup[]
  /** Tool names that may be used without an approval prompt. Auto-approves only — never restricts. */
  autoApproveTools?: string[]
}
```

**Group semantics (normative — an adapter maps its SDK's tool identifiers onto these, never the reverse):**

| group | covers |
|---|---|
| `shell` | executing an OS command in any form, **including** background-process inspection and any general-purpose code-execution tool (a JS REPL counts as shell) |
| `file-read` | reading, listing or searching files |
| `file-write` | creating, editing or deleting files, and persisting memory |
| `web` | fetching URLs and web search |

**Contract rules (security-critical, stated as such):**

- **Absent field or `[]` → today's behaviour byte for byte.** Backward compatible no-op.
- **Deny-only and additive.** Preset-derived groups and explicitly requested groups are **unioned** — a preset can never be weakened by omitting its groups. Duplicates collapse; order is insignificant.
- **Unknown group string → the run is refused before dispatch** with `AdapterToolPolicyError`, not silently dropped. "Silently dropping an unrecognized entry from a security policy would enforce less than was asked for."
- **A deny outranks `autoApproveTools`.** Auto-approval can never re-widen a denied group.
- **A deny outranks an M15 path-scope allow rule.** Where both land on the same rule surface, the M18 deny is applied **last** and is never re-widened by an M15-generated allow rule.
- **Deny-shaped for the consumer, allow-shaped inside the adapter.** Wherever the SDK supports it, the adapter derives a **residual allow-list** from the requested groups and uses deny entries only as a backstop. The invariant: *a built-in the library has never heard of is blocked, not allowed.* A deny-only adapter (no allow-list primitive) is fail-open on future built-ins by construction and is therefore capped at `soft` strength.

### `autoApproveTools` — the rename

`allowedTools` read as a restriction, was documented as nothing, and was silently ignored by three of four adapters. It is now `autoApproveTools`, documented as *auto-approve, never restrict*, and an adapter with **no auto-approval primitive must emit exactly one `warning` event for the run** when the field is supplied, instead of ignoring it in silence.

## 2. Probe and capability flags

Strength is **not** carried by the capability bool — it is a separate axis, and a consumer that needs to know before committing calls a synchronous probe:

```ts
// true iff SOME gating mechanism exists on this adapter. Says nothing about
// coverage or strength — true even when only some groups are enforceable.
architectureCapabilities(arch).toolGating: boolean

// Synchronous, runs BEFORE dispatch. One record per requested group.
probeToolGating(arch, requestedGroups: ToolGroup[]): Array<{
  group: ToolGroup
  enforceable: boolean
  strength: 'hard' | 'soft' | 'none'
  escapeSurfaces: string[]   // canon list of documented bypasses
}>
```

`probeToolGating` sits beside the existing path-scope probe M15 requires. It must be synchronous and pre-dispatch on purpose: a startup *event* arrives too late for a consumer to decline the run.

**Strength axis:**

- `hard` — enforced outside the model (OS sandbox posture, or server-side refusal before execution).
- `soft` — the tool is removed from the model's context/catalog. A model-behaviour gate, not a sandbox.
- `none` — no primitive; requesting this group refuses the run.

**A group with a documented escape surface is never reported `hard`** — the probe reports `soft` and names the surface.

## 3. Per-adapter support matrix

| adapter | `toolGating` | `shell` | `file-read` | `file-write` | `web` | native mechanism |
|---|---|---|---|---|---|---|
| claude-code (A01) | ✅ | soft ⚠ | soft ⚠ | soft | soft ⚠ | residual allow-list on `options.tools`, `disallowedTools` as backstop (strips the tool from model context) |
| codex (A02) | ⚠️ partial | **none → throws** | **none → throws** | hard, coarse | hard, coarse | `sandboxMode: 'read-only'` + the SDK web-search toggle; no per-tool primitive |
| opencode (A03) | ✅ | hard ⚠ | hard ⚠ | hard ⚠ | hard ⚠ | server-side `permission` buckets (e.g. `{ edit: 'allow', bash: 'allow' }`) with a `'*'` wildcard default; a denied tool is refused before execution, not prompted |
| gemini (A04) | ✅ | soft ⚠ | soft | soft | soft | `excludeTools`, applied when the tool registry is built — **before** the approval policy runs |

**claude-code (A01).** The deny rides **only** the built-in allow-list plus the `disallowedTools` backstop — **never** the settings `permissions.allow` / `permissions.deny` surface, because that surface is shared with M15 soft path-scope and `autoApproveTools` and could be re-widened. The SDK's native `permissionMode: 'plan'` is still avoided: it would also defer consumer-curated MCP tools, which M18 explicitly does not gate. Escape surfaces: (a) a spawned subagent does not natively inherit the parent's denies (closed by the M06 propagation below — until then `shell` is `soft`); (b) with `shell` allowed, native builds can serve search through the shell, so a `file-read` deny is bypassable; (c) a built-in MCP web-fetch identifier the deny mechanism does not reliably filter, capping `web`.

**codex (A02).** `file-write` maps onto the whole-run `sandboxMode: 'read-only'` posture — hard, but coarse: reads and the shell stay live. `web` maps onto the SDK web-search toggle. `shell` and `file-read` have **no primitive at all** (`ThreadOptions` has no shell toggle; the permission-profile family that could express read-denial is incompatible with the sandbox posture and unreachable through config passthrough because nested keys are flattened into dotted paths by raw concatenation without quoting). Requesting either **refuses the run pre-dispatch** — the fail-closed exception to codex's usual warn-and-degrade. Nothing is partially applied. Consequence: `planMode: true` on codex now refuses, rather than silently delivering a read-only sandbox with a live shell. The three `sandboxMode` inputs (`codex_sandboxMode`, `additionalDirectories`-derived scope, M18 `file-write` deny) compose by *narrowest wins* on the single field — it is never assigned twice.

**opencode (A03).** The strongest of the four: the adapter stops asserting a blanket allow and derives permission buckets from the deny-groups, defaulting the remainder through the wildcard. A `file-read` deny must cover the file, listing, search and language-service buckets **plus the delegation bucket** — otherwise reads get laundered through a subagent. Escape surface: the server's permission schema ends in a catch-all, so an unknown or mistyped bucket name is **accepted and silently ignored, with no validation error**; the adapter may claim `hard` only for buckets confirmed against the running server version (the SDK does not bundle the server, so the pin, the resolved SDK and the installed binary can be three different versions). Plan mode here was previously a logged no-op and is now genuinely enforced.

**gemini (A04).** Exclusion happens in the tool registry, so a denied tool is never registered and never reaches the model — and an auto-approving `yolo` mode does **not** bypass it, because there is nothing registered to approve. But `excludeTools` is **deny-only with no allow-list counterpart**, so gemini cannot satisfy the residual-allow-list invariant: a built-in added by a peer-SDK bump stays available until the group mapping names it. That is why every gemini group is capped at `soft`. A `shell` deny must also exclude the **background-process tools**, which are registered outside the enumerated built-in set. The old hardcoded plan-mode exclusion list (`write_file`, `replace`, `run_shell_command`, `save_memory`) is removed and subsumed by the group mapping. Tool renames that leave a legacy alias resolvable mean a deny must name **both spellings** or it silently fails to fire.

## 4. Degradation — fail-closed

1. **Unenforceable → throw before dispatch.** No primitive for a requested group on the target adapter → refuse the run with `AdapterToolPolicyError`. Never mid-stream, and **no partial application** of the remaining enforceable groups.
2. **Enforceable but `soft` → run, and say so.** Strength and escape surfaces are reported through `probeToolGating` and a startup event.
3. **Porous combination → exactly one `warning` for the run.** Groups are independent (denying `file-write` does not auto-deny `shell`), but denying `file-read` or `file-write` while `shell` stays available is **not a filesystem boundary**. The run proceeds; the warning states that plainly.

This is the opposite posture from M15 path-scoping, which warns and continues. A run declaring both can be refused by its M18 half where its M15 half would only have warned — which is why M18 is its own module and was **not** folded into M15.

## 5. Plan mode is now a preset

`planMode: true` desugars into a named, exported preset constant:

```ts
planMode: true   →   disallowedToolGroups: ['file-write', 'shell']
```

Reads and web stay available — plan mode must still be able to research. The preset is **not a weaker mode**: it produces identical deny-groups and inherits the fail-closed posture, so an adapter that previously ignored plan mode with a console warning now **throws**. The documented opt-out is an explicit empty `disallowedToolGroups`. Every adapter's plan-mode handling goes through the deny-group path; there are no per-adapter plan-mode special cases left.

M01 also gains the general convention this is the first instance of — a **preset registry**: a module may publish a named library-built constant that desugars a coarse consumer flag into a fine-grained contract. The registry is canon in the owning module and exported at L4.

## 6. Blast radius across the rest of the system

**Subagents (M06) — propagation is mandatory.** A `SubagentDefinition` may narrow tools but may **never widen past the parent run's effective policy**. A run's deny-groups are resolved against each subagent's own toolset and applied to **every definition the run spawns**, including definitions authored before tool gating existed. Without this, "deny the shell" would mean "deny the shell until the model delegates". A definition naming a tool from a denied group is **not an error** and does not fail the run — the intersection wins silently. If an adapter cannot propagate a deny into subagents, that group is reported with the subagent escape surface and **never as `hard`**; the run still proceeds.

**Skills (M05).** A `shell` deny **suppresses the skill tool entirely** for that run — a skill routinely instructs the model to run shell commands, so leaving it available reopens the group through the front door. On claude-code this **overrides** the whitelist that otherwise keeps `Skill` available under the plan-mode preset. Denies of `file-read`, `file-write` or `web` leave skills untouched. An inline skill still materializes on disk, but the tool is not offered to the model, and the consumer learns this through the deny-reporting channel rather than through silence.

**Background tasks (M17).** A background task *is* a shell task. A run that denies `shell` has **no background-task capability at all**: no `background_task_*` events are emitted and `result.backgroundTasks` is never populated — exactly as on an adapter whose SDK cannot background work. This is a skip, not a degradation to report. The existing disable lever `claude_disallowBackgroundBash` stays independent: it forces backgrounded shell work to run synchronously, whereas an M18 deny removes the shell itself. Both set at once is not a conflict — the deny is the stronger statement and the lever has nothing left to act on.

**MCP (M04) — explicitly out of scope.** M18 gates **built-ins only**. MCP tool names are opaque and cannot be reliably classified as shell/file-read/etc., and guessing wrong in either direction is worse than declining. **An MCP tool is never denied by group**: a run with every group denied can still call every MCP tool it was given, and a filesystem MCP server survives a `file-read` + `file-write` deny. The consumer's only remedy is to withhold the server.

**Resume (M07).** `disallowedToolGroups` joins `allowedPaths` and `disallowedPaths` in the always-immutable `RuntimeExecuteParams` set: *a capability gate must not shrink or grow mid-session — a resume that quietly hands the shell back is the same class of failure as one that widens the sandbox.* `findResumeViolations` is extended to cover it. Because plan mode desugars into that field, **flipping `planMode` on resume is a violation too**, through the same field-level check with no special case.

**Path scoping (M15).** The two modules are ordered, not orthogonal. M15 bounds *where* filesystem access happens; M18 removes *whether* a tool class exists. On claude-code, M15's soft path-scope already flips the run to a default-deny permission mode that pre-approves only the file built-ins — which means declaring path-scope with **no** M18 deny at all nonetheless withholds shell and web: a real capability reduction the consumer did not ask for by name.

## 7. Background-task hold cap is now terminal (M17 / M13)

Independent of tool gating, the control-channel hold's two bounds are now explicitly asymmetric:

- **Grace window** — armed once everything tracked has settled, re-armed by every frame that arrives while parked; it measures *engine silence*. Expiry stays **silent**: the channel closes, the run ends at `result`, no `warning` and no `error`. The last event of a healthy run is its result.
- **Hard cap** on the parked stretch — released the moment a continuation turn begins (from there `timeoutMs` / `abort()` bound it as an ordinary live turn). **Previously (0.9.5) expiry emitted a `warning` and the run continued. Now (0.9.6) it ends the run**: the adapter interrupts and aborts the session down the same path `abort()` uses, and the last stream event is `{ type: 'error' }` carrying a new typed error.

The defect this fixes: closing the control channel under a still-live engine left MCP, `canUseTool`, hooks and elicitation silently dead while the CLI kept running, and the consumer saw only `(<tool> completed with no output)` — a half-dead session, which is a worse failure than a failed one.

Two new error classes join the `AdapterError` hierarchy, **both exported from the package root** (every class in the hierarchy is now exported, not only the base), both distinguishable by `instanceof` **and** by a `.name` string that survives serialization across a process or transport boundary, with `toJSON` carrying the extra fields through:

```ts
class AdapterBackgroundHoldExpiredError extends AdapterError {
  // runtime phase, TERMINAL — nothing follows the `error` event.
  // Carries the cap that was hit as a field, repeats it in the human-readable
  // message alongside the architectureConfig key that moves it
  // (claude-code: `claude_backgroundHoldCapMs`, default 90s).
}

class AdapterToolPolicyError extends AdapterError {
  // Raised BEFORE anything runs — a refusal, not a failure.
  // Carries: the adapter id, the groups that are unenforceable,
  // and the enforceable groups with their strength.
}
```

`AdapterBackgroundHoldExpiredError` must not be confusable with a consumer `abort()` (`AdapterAbortError`) or a consumer timeout (`AdapterTimeoutError`). The cap must stay strictly under the consumer's stream timeout (`collectEvents()` defaults to 120s) — otherwise the helper rejects first, the failure surfaces as a generic timeout, and the specific signal that background work was abandoned is lost. The 90s default preserves that margin.

Related contract clarification in M01/M12: **a `warning`'s position on the stream carries no meaning at all** — it is side-band, a trailing `warning` never makes an adapter non-conforming, and anything that truly *ends* a run must be an `error`, never a `warning`. The conformance toolkit asserts terminality against the last non-`flush`, non-`warning` event.

## 8. Conformance

- New e2e scenario in the shared catalog: **`tool-gating`** — "a denied `ToolGroup` is unusable for the whole run — its tools are absent from the adapter's catalog, or the run is refused before dispatch — and a documented escape surface behaves as the matrix says it does, not better." Real-model runs matter more here than replay: only a live model distinguishes *the tool is gone* from *the model chose not to use it*.
- The existing **`plan-mode`** scenario is re-pointed at M18: mutation blocked, reads and web still working, and an adapter that cannot enforce the preset **refuses the run pre-dispatch rather than warning**.
- **One negative test per documented escape surface**, so closing a hole (e.g. M06 subagent propagation) shows up as a flipping test.
- The residual-allow-list invariant is tested on **the shape sent to the SDK**, not just on today's tool-set behaviour.
- The claude-code background-tasks scenario keeps its wake-up matrix over `{backgrounded bash, subagents} × {one-shot, streaming}`, and its silence assertion is strengthened: a settled run must emit **neither** a hold-bound `warning` **nor** an `AdapterBackgroundHoldExpiredError`.
- The `claude_disallowBackgroundBash: true` criterion gains a conclusiveness precondition: it is absence-shaped, so a transcript in which the model never actually attempted `run_in_background: true` is **inconclusive**, not passing.
