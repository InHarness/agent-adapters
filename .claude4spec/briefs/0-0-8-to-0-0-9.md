# Brief: 0.0.8 → 0.0.9

This release establishes a **real-model end-to-end (e2e) conformance regime** for the adapters library. Before 0.0.9 the spec described capabilities but had no canonical answer to "what does a live-model test have to prove, and which of those does each adapter actually cover?" This release fills that gap: it defines a shared catalog of 14 real-model scenarios, records the claude-code adapter's coverage against it (9 covered, 7 planned), ties the declared peer-SDK version range to the SDK version the suite actually runs against, and adds a contract for rejecting an out-of-range SDK at init. Nearly every change is testing/verification scaffolding for the `claude-code` adapter (A01); no runtime capability of the adapters themselves changed. 13 new acceptance-criteria records were added to pin these rules down.

## The canonical e2e scenario catalog (M12)

M12 (conformance-release) now owns a shared vocabulary of **14 real-model e2e scenarios** — the single definition of what each kind of live-model test proves. Adapters reference these names; they don't redefine them. The catalog:

| Scenario | What a live-model run must prove |
|---|---|
| `simple-text` | model streams `text_delta`s, emits a well-formed `result` + usage; run for both the alias and the full model id |
| `thinking` | reasoning surfaces as `thinking` events, distinct from answer text |
| `tool-use` (MCP) | a configured MCP tool is invoked and its `tool_result` flows back into the model's answer |
| `subagents` | `subagent_*` lifecycle events carry a consistent `subagentTaskId`; a consumer-defined subagent is invocable where supported |
| `plan-mode` | mutations blocked, reads allowed (or a warning where the SDK cannot enforce it) |
| `path-scope` | reads/writes confined to `cwd ∪ allowedPaths`; a path outside scope is blocked |
| `resume` | a resumed session recalls turn-1 state; per-call usage is independent |
| `todo` | a task-planning tool projects to `todo_list_updated`, snapshotted on `result` |
| `user-input` | the native ask-user tool bridges to `user_input_request`; the handler's answer reaches the model; the decline path is handled |
| `image` | an image passed on input is materialized and described by the model |
| `mid-turn` | `pushMessage` mid-turn is accepted and reflected as a `user_message` in the same run |
| `abort` | `abort()` mid-stream ends the run cleanly (`AdapterAbortError`, input channel closed) |
| `unknown-model` | an unknown alias warns and passes through — the SDK, not the adapter, rejects it |
| `usage` | billing tokens vs `contextSize` and cache buckets are legible on `result` |

M12 also gains a step in its **Contract-extension checklist**: whenever a new event or field introduces a new real-model scenario, that scenario must be (1) added to this catalog, (2) recorded in each covering adapter's e2e coverage list, and (3) given its own acceptance-criteria record.

## claude-code (A01) e2e coverage

The claude-code adapter's `e2e coverage` section is rewritten to a coverage table against the catalog. The suite is **parametrized over the M02 model catalog** via the `E2E_CLAUDE_MODEL` env var and the `test:e2e:claude:*` npm scripts, and runs against a dev-pinned SDK `claude-agent-sdk@^0.3.153` (this dev-pin is the "verified range" evidence — see below).

- **Covered (9):** `simple-text`, `thinking`, `tool-use` (in-process MCP), `subagents` (incl. a consumer-defined subagent), `plan-mode` (blocks writes / allows reads / keeps MCP executable), `todo` (TodoWrite → `todo_list_updated`), `user-input` (AskUserQuestion + decline path), `resume` (turn-2 recall + per-call usage), `abort`, `unknown-model` (warn + passthrough).
- **Planned (7):** `image` (base64 / url / file → described), `mid-turn` (real `pushMessage` round-trip → `user_message`), `path-scope` (`allowedPaths` / `disallowedPaths`), `usage` (billing vs `contextSize`, cache buckets), MCP elicitation (`elicitation_request` / `onElicitation`), model-matrix (core scenarios × full M02 catalog), and error/resilience (`timeoutMs` timeout, out-of-range SDK).

## Verified-range discipline & SDK version gate

Two connected rules were made binding:

1. **Verified range = evidence.** The SDK version the e2e suite actually runs against (dev-pinned `^0.3.153`) is the evidence for the declared `peerDependencies` range. A peer-SDK bump must **re-run the full e2e suite before the declared range is narrowed** — the declared range must equal the verified range. (ACs `ac-e2e-suite-is-the-verified-range-evidence`, `ac-claude-code-e2e-verified-range-evidence`.)

2. **Out-of-range SDK is rejected at init.** Installing `claude-agent-sdk` outside the declared peer range must emit an init-phase `AdapterInitError` whose message names the mismatch — of the form "installed X requires Y" — and this error is **non-suppressible**. This is a new contract; **the version gate is not yet implemented in code** (only the planned `sdk-version-gate` e2e scenario and the ACs `ac-out-of-range-sdk-version-emits-adapterin`, `ac-claude-code-e2e-sdk-version-gate` exist so far).

## New acceptance criteria (13)

All 13 new records are `ac` entities pinning the above:

- **Verified-range:** `ac-e2e-suite-is-the-verified-range-evidence`, `ac-claude-code-e2e-verified-range-evidence`.
- **SDK version gate:** `ac-out-of-range-sdk-version-emits-adapterin` (out-of-range install → non-suppressible init `AdapterInitError`), `ac-claude-code-e2e-sdk-version-gate` (edge-case e2e for it).
- **MCP elicitation:** `ac-mcp-elicitation-bridges-elicitation-req` (SDK `elicitation_request`/`onElicitation` bridges to `user_input_request`, answer reaches the model), `ac-claude-code-e2e-mcp-elicitation-scenario` (live e2e for it).
- **claude-code e2e scenarios:** `ac-claude-code-e2e-model-matrix-scenario` (core scenarios × M02 catalog via `E2E_CLAUDE_MODEL`), `ac-claude-code-e2e-image-scenario`, `ac-claude-code-e2e-mid-turn-scenario`, `ac-claude-code-e2e-path-scope-scenario`, `ac-claude-code-e2e-usage-scenario`, `ac-claude-code-e2e-timeout-scenario` (exceed `timeoutMs` → runtime-phase `AdapterTimeoutError`, input channel closed), `ac-claude-code-e2e-os-sandbox-degrade` (OS sandbox requested on a host without bubblewrap/seatbelt → path-scope degrades hard-to-soft with a warning).

## For implementers

These are test-harness and one runtime contract targets for the `claude-code` adapter. No shipped adapter behavior changed except the (still-unimplemented) version gate.

1. **e2e scripts & model matrix.** Ensure `package.json` exposes `test:e2e:claude:*` scripts and that the claude-code e2e runner reads the `E2E_CLAUDE_MODEL` env var to select the model, iterating the M02 model catalog for the model-matrix scenario. Suite must skip cleanly when live-model creds are absent (shared L5 convention).
2. **Dev-pin the SDK.** Keep `claude-agent-sdk` dev-pinned to `^0.3.153` (devDependencies) as the verified-range evidence; do not narrow the `peerDependencies` range without re-running the full e2e suite.
3. **Implement the 7 planned e2e scenarios** for claude-code, asserting live-model behavior:
   - `image`: pass base64 / url / file image input; assert the model returns a description.
   - `mid-turn`: call `pushMessage` mid-run; assert it surfaces as a `user_message` in the same run.
   - `path-scope`: set `allowedPaths` / `disallowedPaths`; assert reads/writes confined to `cwd ∪ allowedPaths`, a path outside scope blocked (`disallowedPaths` precedence).
   - `usage`: assert billing tokens vs `contextSize` and cache buckets are legible on `result`.
   - `mcp-elicitation`: drive SDK `elicitation_request` / `onElicitation`; assert it bridges to `user_input_request` and the answer reaches the model.
   - `timeout` (edge): exceed `timeoutMs`; assert `AdapterTimeoutError` at runtime phase with the input channel closed.
   - `os-sandbox-degrade` (edge): request the OS sandbox on a host lacking bubblewrap/seatbelt; assert path-scope degrades hard-to-soft and emits a warning.
4. **Implement the SDK version gate (new code).** At adapter init, compare the installed `claude-agent-sdk` version against the declared peer range; if out of range, throw a non-suppressible `AdapterInitError` at the init phase with a message of the form "installed X requires Y". Add the `sdk-version-gate` e2e scenario asserting this.
5. **When adding any new event/field** to an adapter contract, follow the M12 extension checklist: add the scenario to the M12 catalog, record it in each covering adapter's coverage list, and add a matching `ac` record.
