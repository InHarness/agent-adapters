# Brief: 0.0.1 → 0.0.2

This release adds **filesystem path scoping** to the unified adapter layer. A consumer can now declare, in engine-neutral terms, which directories an agent's tools may touch — and each adapter maps that intent onto its SDK's native sandbox primitive (or warns when it has none). The goal is a single, portable way to say "this run may only read/write under these paths" without writing per-engine sandbox config. The feature is purely additive: when the new fields are absent, every adapter behaves exactly as in 0.0.1.

## The two new config fields

Two optional fields were added to `RuntimeExecuteParams` (type home: the unified core, `src/types.ts`):

```ts
allowedPaths?: string[]     // absolute directory prefixes the agent's tools may access
                            // beyond the implicit base (cwd)
disallowedPaths?: string[]  // carve-outs excluded from the allowed set
```

Semantics:

- **Precedence:** `disallowedPaths` > `allowedPaths` > implicit base (`cwd`). A path matched by `disallowedPaths` is blocked even if it sits inside an `allowedPaths` root.
- **Scope:** read AND write combined (no separate read/write split today — that is a noted future extension, along with glob support).
- **Relative paths are normalized, not rejected** — a relative entry is resolved against `cwd` before mapping.
- **Both absent/empty = no-op** — identical to 0.0.1 behavior (backward compatible).
- Path-scope composes **additively** with plan mode: both only ever narrow access; neither overwrites existing engine sandbox config.

## Capability advertisement and gate strength

A new flat capability flag is exposed: `architectureCapabilities(arch).pathScope: boolean` — advertises whether an adapter honors `allowedPaths`/`disallowedPaths` at all. It uses the same flat-bool mechanism as the existing `midTurnPush` flag.

Crucially, `pathScope` does **not** encode how strong the enforcement is. **Gate strength** (hard vs soft) is carried as a *separate* signal, because the flat capability map intentionally stays boolean — graduated capabilities are owned by the feature module, not folded into the map.

- **Hard gate** = OS-syscall enforcement (the kernel blocks out-of-scope filesystem access).
- **Soft gate** = model-visible permission rules only (the agent is *told* not to, but nothing at the OS level stops a subprocess).

A consumer building a real security sandbox MUST obtain the **runtime-confirmed** gate strength (via a probe/startup signal) **before** dispatching work. A post-hoc `warning` is explicitly insufficient, and `architectureCapabilities` reporting "hard-capable" is a static fact, NOT a runtime guarantee that hard enforcement is active on this host.

## Degradation contract

1. **Unsupported adapter** (opencode, gemini): emit a one-shot `warning`, run the operation unscoped, never throw for "unsupported".
2. **Hard → soft at runtime** (claude-code on a host lacking bubblewrap/seatbelt): emit a `warning` that the gate is model-visible, not OS-enforced. The hard guarantee silently downgrades to soft.
3. **claude-code with OS sandbox enabled:** filesystem operations outside the declared scope — including a Bash subprocess writing out of scope — are blocked at the **syscall level**. Under the soft default, only `Bash(...)` / `Read` / `Edit` permission patterns offer (model-visible) protection.

## Path scope is frozen for a session's lifetime

Session resume now treats path-scope fields as **immutable**. The resume-validation set was extended beyond architecture-option keys to also cover designated `RuntimeExecuteParams` fields: `allowedPaths` and `disallowedPaths` may not change on a resumed session. `findResumeViolations` reports any change to either field before a resumed run. Rationale: a sandbox must not be re-scoped mid-session — to change the scope, the consumer must fork a new session.

## Acceptance criteria (observable contract)

The release pins eleven acceptance criteria for the feature:

- `allowedPaths`/`disallowedPaths` are immutable on resume; `findResumeViolations` reports any change to either before a resumed run.
- With both fields absent, run behavior is identical to today (no-op, backward compatible).
- Precedence holds: `disallowedPaths` overrides `allowedPaths`, which overrides the implicit base (`cwd`).
- Gate strength (hard vs soft) is exposed as a signal separate from the `pathScope` bool and is confirmable before dispatch, not only via a post-hoc warning.
- On a host without an OS sandbox, a hard-capable adapter (claude-code) degrades hard→soft and emits a warning that the gate is model-visible, not OS-enforced.
- `architectureCapabilities(arch).pathScope` advertises whether an adapter honors the fields at all.
- On claude-code with the OS sandbox enabled, filesystem operations outside the declared scope are blocked at the syscall level (hard gate).
- An adapter lacking support (opencode) emits a one-shot warning and runs the operation unscoped, never throwing for "unsupported".
- A relative path in `allowedPaths`/`disallowedPaths` is normalized against `cwd` before mapping (not rejected), and path-scope composes additively with `planMode` (both narrow).
- A `disallowedPaths` carve-out is not guaranteed on an allow-list-only adapter (codex) and is surfaced as an expressiveness limitation, so consumers do not assume an unenforced deny.
- A Bash subprocess writing outside scope is blocked at the syscall level when the OS sandbox is enabled, and only soft-protected under permission rules.

## For implementers

1. **Unified types** (`src/types.ts`): add to `RuntimeExecuteParams`:
   ```ts
   allowedPaths?: string[];
   disallowedPaths?: string[];
   ```
   These declare a filesystem sandbox for the agent's tools; precedence is `disallowedPaths` > `allowedPaths` > `cwd`. Absent fields preserve current behavior.
2. **Capability map** (`architectureCapabilities` in `src/models.ts`/`src/index.ts`): add `pathScope: boolean` to each adapter's entry — `true` for claude-code and codex, `false` for opencode and gemini. Keep the map flat-bool; do NOT encode strength here.
3. **Gate-strength signal:** expose hard/soft/none as a *separate*, runtime-confirmable signal (probe/startup event), distinct from the `pathScope` bool, so a consumer can verify enforcement before dispatch.
4. **claude-code adapter** (`src/adapters/claude-code.ts`): map `disallowedPaths` → `permissions.deny: ['Read(<p>)','Edit(<p>)', ...]`; `allowedPaths` → `additionalDirectories`. When `sandbox.enabled`, merge `sandbox.filesystem` rules into the same Read/Edit rule set and rely on OS enforcement (bubblewrap/seatbelt). If the host lacks an OS sandbox at runtime, emit a hard→soft `warning`.
5. **codex adapter** (`src/adapters/codex.ts`): map `allowedPaths` → `sandboxMode: 'workspace-write'` + `additionalDirectories`; full block → `sandboxMode: 'read-only'`. Compose with (never overwrite) existing `codex_sandboxMode`/`additionalDirectories` and plan mode. Surface any `disallowedPaths` carve-out inside an allowed root as an unsupported/expressiveness warning — codex cannot enforce deny inside an allow-listed root.
6. **opencode adapter** (`src/adapters/opencode.ts`) and **gemini adapter** (`src/adapters/gemini.ts`): on any `allowedPaths`/`disallowedPaths`, emit one one-shot `warning` and run unscoped; never throw. (For gemini, verify whether `targetDir`/include-directories can back a soft gate — if so, flip `pathScope` to `true`/soft.)
7. **Path normalization:** before mapping, resolve relative entries in `allowedPaths`/`disallowedPaths` against `cwd`.
8. **Session resume** (`findResumeViolations`, `src/adapters/.../resume` logic in the session-resume module): extend the immutable-field check beyond `ArchOption` keys to also flag any change to `allowedPaths`/`disallowedPaths` on resume; report it as a violation so the run is rejected (consumer must fork a new session to re-scope).
