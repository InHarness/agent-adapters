# Brief: 0.9.7 → 0.9.8

This release closes a hole in the subagent lifecycle contract. Until now a consumer that paired `subagent_started` with `subagent_completed` live could be left holding an unmatched pair forever: if the run was terminated (`abort()`, `timeoutMs`, or a background-hold cap expiry) while a subagent was still running, the stream simply ended and the started event never got its counterpart — so the consumer's "clean up when every subagent is closed" step never fired. 0.9.8 makes the adapter responsible for closing what it opened, and at the same time turns `subagent_completed.status` from a pass-through of whatever the underlying SDK happened to spell into a **unified four-value vocabulary that adapters must map onto**. A secondary correction: `codex` is now stated to emit *no* subagent lifecycle events at all, rather than "synthesized" ones.

The rationale for splitting the vocabulary is that a consumer reacts differently to "the whole run is over" and "one delegation ended while the run keeps producing" — and the old contract could not express the difference.

## 1. `subagent_completed.status` is now a unified, adapter-mapped vocabulary

`status` carries exactly four values, and their meanings are fixed:

| value | meaning |
|---|---|
| `'completed'` | the subagent ran to its own end |
| `'failed'` | the subagent ended in error |
| `'aborted'` | the subagent was closed because a **run-level** termination ended the run |
| `'stopped'` | the subagent was ended **individually** by a stop control while the run continued (the per-task lever reserved by the background-tasks module, M17) |

`'aborted'` and `'stopped'` are deliberately distinct: the first says the run is over, the second says one delegation ended while the run keeps producing.

**Mapping is adapter-owned, total, and ordered.** Adapters map their SDK's own spelling onto these four names and **never forward it raw**. Wire values must not be matched against this set directly. The mapping rules, in order:

1. A spelling the adapter recognizes → its declared counterpart.
2. An unrecognized but **cancellation-shaped** spelling (the SDK's way of saying work was stopped by a termination) → `'aborted'`.
3. A spelling that fits no shape at all → `'failed'`, **and** raise a `warning` event — **at most one `warning` per run**, however many unrecognized statuses arrive during it.
4. **Never `'completed'`** for an unrecognized value. A false claim of success is the one error a consumer would act on irreversibly.

That `warning` is explicitly framed as a **drift signal, not a capability degradation** — nothing was requested and refused; an SDK status arrived that is outside anything the pinned SDK range ever declared. It is the signal that the next SDK-pin verification pass has to investigate.

### Per-adapter mapping as specified

**claude-code (A01).** `task_notification.status` is a **closed union today**: `completed` / `failed` / `stopped`. It is mapped, not forwarded; `stopped` maps to unified `'stopped'`. Note that the sibling `task_updated` channel already exposes a wider engine vocabulary including `cancelled` / `canceled`, which is cancellation-shaped — hence rule 2 above. `Query.stopTask()` is not called by this adapter today, so no adapter-initiated call currently produces `'stopped'`.

This is also recorded as a **schema-drift point**: `task_notification.status` is a closed union while `task_updated.patch.status` already shows the wider engine vocabulary; a peer-SDK bump inside the declared range `>=0.3.0 <0.4.0` could widen the notification union to match. An open probe is filed against the verified pin `0.3.210`: whether `Query.interrupt()` settles in-flight tasks as `'stopped'` — if it does, a single `abort()` could theoretically yield both `'stopped'` (from the SDK) and `'aborted'` (from the adapter's own flush) in one run, blurring the distinction the vocabulary just introduced.

**gemini (A04).** A subagent thread's `agent_end` maps **by `reason`**:

```
reason: 'failed'  → status: 'failed'
reason: 'aborted' → status: 'aborted'
otherwise         → status: 'completed'
```

The reason is native on this SDK, so the abort case is *reported*, not inferred — mapping it to `'completed'` would falsely claim success.

## 2. Run-level termination closes every still-open subagent

New rule, binding on every adapter:

> A run-level termination fires with subagents in flight — `abort()`, `timeoutMs`, or a hold-cap expiry (M13) → every subagent the adapter still has open is closed with a `subagent_completed` carrying `status: 'aborted'` before the stream ends, whether the run ends with a terminal `error` or by natural iterator completion.

This is deliberately the **opposite** of the rule for `background_task_*` events. A background task outlives the run and only the engine can honestly report its completion, so on a cap expiry a remaining background task is *abandoned* with its completion never reported. A subagent, by contrast, ends *with* the run, so the adapter is the party that can report its end truthfully — subagents are closed rather than abandoned. That asymmetry is now stated explicitly on both sides.

**The flush reports on the adapter's tracking, not on the subagent.** A synthesized `subagent_completed` means *this run stopped tracking that subagent* — not that the helper agent's own execution ended. Consumers may use the flush to close their own bookkeeping, but may **not** read it as evidence that every delegated task actually stopped.

### Per-adapter flush behaviour

**claude-code (A01).** On run-level termination, in addition to the existing abort sequence (interrupt, controller abort, input-channel close), the adapter walks its **in-flight task-id set** — ids that were started but not yet settled by a `task_notification` — and emits `subagent_completed` with `status: 'aborted'` for each, before the stream ends.

A trap is called out explicitly: the `Map<task_id, task_type>` that routes subagent kinds away from the background-tasks path (M17) is **not** this set. That map never removes entries, so walking it instead would incorrectly re-close every subagent the run ever started.

**gemini (A04).** On the run's `agent_end` with `reason: 'aborted'`, each thread still in the active set is closed with a synthesized `subagent_completed` (`status: 'aborted'`) before the stream ends. This is a backstop for threads that never got their own `agent_end`; a thread that already received one is not double-closed.

**opencode (A03).** With a `task` subagent in flight, the tracked `subagentTaskId` is closed with a synthesized `subagent_completed` (`status: 'aborted'`) before the stream ends. Because A03's subagent attribution is **ordering-based under a single-active assumption**, the flush closes exactly the **one** subagent the adapter was tracking — a nested or concurrent `task` was never opened as its own tracked pair, so nothing is closed or claimed for it.

**codex.** No subagent concept — nothing to flush (see §3).

## 3. New invariant: at most one `subagent_completed` per `subagent_started`

> At most one `subagent_completed` per `subagent_started`.

A subagent that already reported its own end **is closed**; the termination flush applies only to those still open. The spec attaches an implementation note that is the whole point of the invariant:

> An adapter that tracks started ids and settled ids in the same structure cannot satisfy this — the open set must be the one the settle path empties.

## 5. Conformance and release policy

**Two conformance invariants, and they must be asserted together.** The shared assertion toolkit gains:

1. **Lifecycle pairing** — every `subagent_started` is matched by a `subagent_completed` before the stream ends, on every terminal path including abort, timeout and hold-cap expiry.
2. **At most once** — no `subagent_started` is matched by two `subagent_completed` events.

The rationale is stated: pairing alone does not catch a flush that double-closes already-settled subagents, so asserting only one of the two lets that defect pass.

**The `abort` e2e scenario is extended.** Scenario catalog row:

- before: `abort() mid-stream ends the run cleanly (AdapterAbortError, channel closed).`
- after: `abort() mid-stream ends the run cleanly (AdapterAbortError, channel closed); and, with a subagent in flight, the lifecycle family is closed before the stream ends rather than left as an unmatched subagent_started.`

**claude-code's e2e coverage status for `abort` is downgraded**, honestly, from `✅ covered` to:

> `⚠️ partial — abort mid-stream is covered; the subagent leg (a run-level termination with a subagent in flight closes the lifecycle pair, exactly once) is not implemented yet`

**Semver policy — new rule.** Adding a new **value** to an already-declared vocabulary is additive and therefore a **minor** bump, on the same footing as a new event or a new param. But:

> Where the field is typed loosely enough that a consumer's exhaustive `switch` gets no compiler warning, the behavioral CHANGELOG note is not optional — it is the consumer's only signal.

This applies directly to this very release: `status` on `subagent_completed` is currently typed `string` in `src/types.ts:203`, so no consumer gets a compiler warning about the new `'aborted'` / `'stopped'` values. A behavioral CHANGELOG note is mandatory here.

## 6. New acceptance criteria

Seven acceptance criteria were added (verbatim), tagged to the subagents module (`m06`), the claude-code adapter (`a01`) and the gemini adapter (`a04`):

Requirements:

- The claude-code adapter maps the SDK's task status onto the unified `subagent_completed.status` vocabulary rather than forwarding it. *(a01)*
- A gemini subagent thread whose `agent_end` carries `reason: 'aborted'` is reported with `status: 'aborted'`, not `'completed'`. *(a04)*
- A `subagent_completed` synthesized on run-level termination carries `status: 'aborted'`. *(m06)*

Edge cases:

- When a run-level termination ends a run, every subagent the adapter still has open is closed by a synthesized `subagent_completed` before the stream ends.
- A subagent that already reported its own `subagent_completed` is not closed a second time by the termination flush.
- An SDK task status the adapter does not recognize, and which is cancellation-shaped, maps to `subagent_completed.status: 'aborted'`.
- An SDK task status the adapter recognizes as neither declared nor cancellation-shaped maps to `subagent_completed.status: 'failed'` and raises at most one `warning` per run.

## For implementers

Ordered by dependency — the status vocabulary first, then per-adapter mapping, then the termination flush, then conformance.

1. **Define the unified status vocabulary.** In `src/types.ts:203`, the `subagent_completed` variant is currently:
   ```ts
   | { type: 'subagent_completed'; taskId: string; status: string; summary?: string; usage?: UsageStats }
   ```
   Introduce and export the closed union (e.g. `export type SubagentStatus = 'completed' | 'failed' | 'aborted' | 'stopped'`). Narrowing `status: string` to `status: SubagentStatus` is the honest shape, but it is a **breaking type change** for consumers who assign arbitrary strings — if you keep `string` for this release, the mandatory CHANGELOG behavioral note from §5 applies and must be written.

2. **Add a shared mapping helper**, in `src/subagents.ts`, along the lines of `mapSubagentStatus(raw: string, declared: Record<string, SubagentStatus>): { status: SubagentStatus; warn: boolean }`. It implements the ordered rules from §1: declared spelling → its counterpart; unrecognized-but-cancellation-shaped (match `cancel`/`abort`/`interrupt` spellings, incl. `cancelled`/`canceled`) → `'aborted'`; anything else → `'failed'` with `warn: true`. It must never return `'completed'` for an unrecognized value.

3. **Per-run `warning` dedup.** The `warning` from rule 3 fires **at most once per run**. Hold a per-run boolean next to the adapter's other run state, not a module-level flag (a module-level flag leaks across runs and suppresses the second run's signal entirely).

4. **claude-code — map the status.** `src/adapters/claude-code.ts:1905` currently emits `subagent_completed`; route its status through `mapSubagentStatus` with the declared union `completed | failed | stopped` (`stopped` → `'stopped'`). Do not forward `task_notification.status` raw.

### Open probe carried into this release

Whether claude-code's `Query.interrupt()` settles in-flight tasks as `'stopped'` on the verified pin `0.3.210` is **unresolved**. If it does, a single `abort()` can produce both a `'stopped'` (from the SDK) and an `'aborted'` (from the flush) for the same run.
