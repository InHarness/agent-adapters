# Brief: 0.9.11 → 0.9.12

This release is about **agents talking to agents**. Until now a subagent was a one-shot: the model spawned it, it reported, its lifecycle bracket closed forever. Claude Code's SDK lets the model *re-enter* a helper it already backgrounded via `SendMessage`, and the library had no contract for that — a second lifecycle pair for a known `taskId` looked like a duplicate, and the control channel could close underneath a resumed helper. 0.9.12 specifies re-entry end-to-end, adds a fifth capability group so delegation can be gated as its own surface, and draws a hard boundary between subagents (which this run spawned) and peers/teammates (which it did not). It also admits, in writing, that the adapter's built-in-tool inventory has drifted badly behind the SDK it is pinned to.

Two changes are breaking in practice; both are called out below.

## Subagent re-entry: one `taskId`, several lifecycle pairs

The central contract correction: **`taskId` identifies the agent, `toolUseId` identifies the invocation.** A `taskId` is no longer a guarantee of a single open/close bracket. When the model re-enters a backgrounded helper, the system emits a *second* `subagent_started` carrying the **same `taskId`** and a **new `toolUseId`** — the id of the re-entering tool call, not the original spawn's — closed by its own `subagent_completed`.

The event shape gains one field:

```
subagent_started  { taskId, description, toolUseId, resumed?: boolean }
subagent_completed { taskId, status, summary?, usage? }
```

`resumed` is **absent** on the first start for a `taskId` and `true` on every start after it. It is not derivable downstream, which is why it has to be on the wire: a re-entered agent's deltas keep resolving `subagentTaskId` from the **original** spawn's tool-use id, so attribution alone cannot tell the cycles apart. Ordering is guaranteed — a `subagent_started { resumed: true }` never precedes the `subagent_completed` of the cycle it re-enters. The pairs sequence cleanly; they do not nest.

**This is breaking for consumers that treat a `subagent_completed` as a terminator.** `splitBySubagent` keys buckets on `subagentTaskId`, never on the pair, so both cycles of a re-entered agent land in the *same* bucket in stream order — the bucket is neither re-created nor split. A consumer that closed the bucket on the first `subagent_completed` will see events arrive after it. The terminator is the **last** completed for that `taskId`, not the first. Cycles can only be told apart by reading the `resumed` marker on the starts inside the bucket.

Termination synthesis was retuned to match: the adapter synthesizes a closing `subagent_completed { status: 'aborted' }` for unpaired starts **"at most once per `taskId` per termination"** (was: "at most once per `taskId`"), because across a whole run one `taskId` may legitimately carry more than one lifecycle pair. If a run terminates in the window between a subagent settling and its re-entry, nothing is synthesized — there is no unpaired start, and that `taskId` simply never sees its second cycle.

### The hold window is the subtle part

Re-entry feeds back into background-task hold logic, and this is where a naive implementation breaks. Grace is armed the moment everything tracked has settled — which is *exactly* the window between a subagent settling and the model re-entering it — and grace expiry closes the control transport. So a settled `taskId` that sees a second `task_started` **returns to the in-flight set and re-arms both hold bounds**.

One bit is not enough. The spec adds this edge case verbatim:

> "A second `task_started` arrives for a `taskId` that the engine has already patched as finished but has **not** yet notified → the id is in the tracked set *and* still carries the finished mark, so "everything tracked has settled" reads true while a live cycle is running. Re-entry must clear the finished mark as well as re-adding the id; otherwise grace arms inside the re-entered cycle."

Concretely: the tracked set needs two independent bits per `taskId` — membership and a *finished* flag — and re-entry must reset **both**. Relatedly, the claude-code adapter's per-task `task_type` map (which routes `task_progress` / `task_notification` for a `task_id` to `background_task_*` for `'shell'` / `'monitor'` / `'workflow'` and to `subagent_*` for subagent kinds) now **refreshes** an existing entry on a repeat `task_started` rather than leaving it stale.

## `delegation`: a fifth capability group

`ToolGroup` gains a member:

```ts
// before
type ToolGroup = 'shell' | 'file-read' | 'file-write' | 'web'
// after
type ToolGroup = 'shell' | 'file-read' | 'file-write' | 'web' | 'delegation'
```

**This is the second breaking change.** Widening the union is minor for producers but breaks any consumer that exhaustively `switch`es on `ToolGroup`.

The group covers spawning, listing or messaging a helper agent: the subagent-spawning tool under every alias (`Task`, `Agent`), and the tools that continue or enumerate one (`SendMessage`, `ListAgents`, and `ListAgents`' current alias `ListPeers`). Denying `delegation` closes the whole delegation surface directly instead of relying on deny-propagation into each spawned subagent's own definition — which is what stops a spawned helper from laundering a read the parent denied. Support at this pin: `soft` on claude-code and gemini, `hard` on opencode, unsupported (throws) on codex.

Three deliberate non-interactions, each of which is a trap if you get it backwards:

- **Fail-closed applies to the unknown, not to the unclassified.** A known built-in carrying no capability of any denied group stays in the residual allow-list. A deny removes a capability *class*, not an unrelated tool that happened to share a construction pass. Denying `file-write` must not cost the run its ability to plan.
- **`planMode: true` does not deny delegation.** The preset still maps to `['file-write', 'shell']`; `delegation` is deliberately excluded, so a plan-mode run can still delegate its research to a helper.
- **Denying a group must not break continuation.** The delegation tools stay present in the `options.tools` allow-list the adapter builds whenever a deny-group is set, so with a deny-group active on claude-code the model can still *continue* a subagent it already spawned.

One adapter-local exception, kept local on purpose: on opencode, denying `file-read` also denies `delegation`, because opencode's server-side permission bucket folds delegation into `file-read`. On opencode the groups are not strictly orthogonal. This was not generalised — doing so would cost every plan-mode run its research subagents.

Aliasing matters here because one tool wears many names. The SDK canonicalises `BashOutput` / `AgentOutput` / `BashOutputTool` / `AgentOutputTool` → `TaskOutput`, and `KillBash` / `KillShell` → `TaskStop`. The task inspector/stopper is classified as **`shell`**, and since it is one tool serving both purposes, a run that denies `shell` cannot read its subagents' task output either. A run that wants delegated work but no shell denies `shell` and accepts that; a run that wants neither denies `shell` *and* `delegation`.

### An open hole on gemini

Gemini's `delegation` members are the SDK's own subagent tools — **`codebase_investigator`, `cli_help`, `generalist` and `confucius`** — registered outside the enumerated built-in set and **named by no group in the adapter's mapping today**. This is recorded as a live defect, not an unfilled cell: one of those tools reads the codebase, so for as long as they go unnamed, a `file-read` deny is bypassable through a spawned helper on gemini — precisely the laundering route opencode closes by folding delegation into `file-read`.

A related correction on gemini: the one-shot warning for an ignored `SubagentDefinition` must **not** claim the SDK lacks a subagent mechanism. gemini-cli-core ships an agent registry, an agent-definition shape, and registers named subagent tools of its own. `subagentDefinition: false` records an *adapter* limitation (it does not translate a consumer `SubagentDefinition` per call), not an SDK gap; the warn-and-ignore degradation is right, the old wording was false.

Gemini's verified-pin log also gained a finding that sets up future work: at `^0.38.0` (resolved `0.38.2`), `excludeTools` — the only gating primitive this adapter has — is **deprecated** in favour of the Policy Engine. The successor surfaces are the positive tool lists `coreTools`, `mainAgentTools`, `allowedTools`, and the policy engine's `ALLOW` / `DENY` / `ASK_USER` vocabulary. These are the only route by which gemini's gating strength could ever rise from `soft` to `hard`. A cutover is a question of when, not whether.

## Peers and teammates are not subagents

The `subagent_*` family now has an explicit boundary: **teammates and cross-session peers are not subagents.** An agent-team teammate, or a peer agent in another session addressing this run, emits no `subagent_started`, no `subagent_completed`, nothing on the unified stream, and no capability flag advertises it. The discriminator: an in-process subagent's message carries a sender task id, a cross-session peer's does not. `subagent_*` covers only agents *this run spawned*.

The claude-code adapter enforces the session boundary rather than merely describing it: it **pins `crossSessionInbound` to `'refuse'` on every run**, so an inbound turn from another local session never reaches the model. The pin is written into `options.settings` and must survive alongside the path-scope permission settings the adapter also writes there — the two features share that object and neither may clobber the other. The adapter additionally confines outbound `SendMessage` to tasks this run started, via a `canUseTool` predicate.

Because a consumer cannot choose this posture, they get to observe it: where an adapter pins an SDK option the consumer cannot set, **the pinned value appears in the redacted `sdkConfig` on `adapter_ready`** (`{ type: 'adapter_ready', sdkConfig }`). `crossSessionInbound: 'refuse'` is the standing case. The rule generalises — any adapter-pinned option must surface there, so a posture the consumer did not choose is at least one they can see.

## The inventory has drifted, and there is now a test for it

The residual-allow-list mechanism is only correct against a list of the built-ins the library actually knows, under every current alias, including deferred ones no published catalog advertises. The spec now states the gap in numbers: **at the claude-code pin the adapter's inventory knows 24 names against a published catalog of 45 — a 29-name shortfall.** An exposed name the inventory does not know is a gate that will fail closed on it at the next deny.

A new conformance scenario, **`sdk-surface-probe`**, makes this measurable: against a live engine at the current dev-pin, the set of built-ins the run actually exposes — including the deferred ones reachable only through a discovery gate — must be *covered by* the adapter's known-tool inventory. The `subagents` scenario was also extended to assert a second lifecycle pair for the same `taskId` marked `resumed`, with the session held open until the resumed helper reports.

`sdk-surface-probe` carries the first documented exception to "every e2e scenario drives the adapter". It may call the peer SDK **directly**, and the exemption is deliberately narrow: it is allowed only when what the scenario records is evidence for the verified-pin log, because that log asks what the *engine* exposes at a pin, and an observation taken through our own mapping layer cannot answer it — an adapter bug and an SDK change look identical from the outside. The scenario asserts nothing about `UnifiedEvent`, and it still runs under the same skip-without-credentials contract as everything else in the suite.

## For implementers

Ordered roughly by dependency — types before the code that switches on them, state shape before the logic that reads it.

1. **Widen the `ToolGroup` union** to `'shell' | 'file-read' | 'file-write' | 'web' | 'delegation'`. Then fix every exhaustive `switch`/mapped type over it — this will not compile silently in consumer code, and that is intentional. Classify the release accordingly in the conformance/semver check.
2. **Map the `delegation` group per adapter.** Members: `Task`, `Agent` (spawn, all aliases), `SendMessage`, `ListAgents`, `ListPeers`. Per-adapter strength: claude-code `soft`, gemini `soft`, opencode `hard`, codex unsupported/throws.
3. **Fix the gemini delegation hole.** Add `codebase_investigator`, `cli_help`, `generalist`, `confucius` to gemini's group mapping. These sit outside the enumerated built-in set, like the background-process tools. Until they are named, a `file-read` deny on gemini is bypassable via a spawned helper.
4. **Add the opencode-local rule**: denying `file-read` also denies `delegation`. Keep it in the opencode adapter — do not lift it into shared logic.
5. **Extend the known-built-in inventory** and its alias canonicalisation: `BashOutput` / `AgentOutput` / `BashOutputTool` / `AgentOutputTool` → `TaskOutput`; `KillBash` / `KillShell` → `TaskStop`; classify the inspector as `shell`. Close as much of the 24-of-45 shortfall as the pinned SDK's published tool-input schemas expose.
6. **Guard the allow-list construction**: whenever any deny-group is set, delegation tools must remain in `options.tools`, and any known built-in carrying no denied capability must remain in the residual allow-list. Keep `delegation` out of the `planMode: true` preset (which stays `['file-write', 'shell']`).
7. **Add `resumed?: boolean` to `subagent_started`.** Absent on the first start for a `taskId`; `true` on every subsequent one. The re-entry start carries the re-entering call's `toolUseId`, not the original spawn's. Deltas keep resolving `subagentTaskId` to the original spawn's `taskId`.
8. **Give the in-flight/tracked set two bits per `taskId`** — membership and a *finished* mark. On a second `task_started`: re-add the id, re-arm both hold bounds, **and clear the finished mark**. Missing that last step arms the grace window inside a live re-entered cycle and closes the control transport under it.
9. **Refresh the per-task `task_type` map** on a repeat `task_started` for a known `task_id` instead of leaving the old entry. Routing stays: `'shell'` / `'monitor'` / `'workflow'` → `background_task_*`, subagent kinds → `subagent_*`, unknown or absent → the subagent path.
10. **Scope termination synthesis per termination**, not per `taskId` for the whole run — synthesize `subagent_completed { status: 'aborted' }` at teardown for whatever is unpaired *at that moment*. Do not synthesize for a task that settled and had not yet been re-entered.
11. **Leave `splitBySubagent` keyed on `subagentTaskId`** and document that a bucket's terminator is the last `subagent_completed` for that `taskId`. Do not split or re-create buckets on a resumed cycle.
12. **Suppress `subagent_*` for non-subagents.** Teammates and cross-session peers emit nothing on the unified stream; discriminate on the presence of a sender task id.
13. **Pin `crossSessionInbound: 'refuse'`** in `options.settings` on every claude-code run, merging with (never overwriting) the path-scope permission settings written to the same object. Add the outbound `canUseTool` predicate confining `SendMessage` to tasks this run started.
14. **Surface adapter-pinned options in the redacted `sdkConfig`** on `adapter_ready`, so a pinned posture stays observable to a consumer who could not set it.
15. **Add the `sdk-surface-probe` e2e scenario**, asserting the live engine's exposed built-ins (including discovery-gated ones) are covered by the inventory. It may call the peer SDK directly — it is verified-pin evidence, not a `UnifiedEvent` assertion — and it keeps the skip-without-credentials contract. Extend the `subagents` scenario with a re-entry cycle marked `resumed`.
16. **Gemini, forward-looking:** `excludeTools` is deprecated at `^0.38.0` (resolved `0.38.2`) in favour of the Policy Engine (`coreTools`, `mainAgentTools`, `allowedTools`, and `ALLOW` / `DENY` / `ASK_USER`). That migration is the only path from `soft` to `hard` gating on this adapter.
