# Brief: 0.9.12 → 0.9.13

This release is about **bounding the parts of a run that the existing clocks could not see**. Until 0.9.12 a run had two consumer-facing bounds — the backstop `timeoutMs` and the idle clock `idleTimeoutMs` — plus a background hold cap inside the claude-code adapter. Between them, a single tool call that hung forever, or a subagent that never came back, was bounded by nothing finer than "the whole run's budget". 0.9.13 adds two optional per-unit caps (`toolCallTimeoutMs`, `subagentTimeoutMs`), makes the background hold cap re-armable so that visibly-working tasks are no longer cut short, and settles the rule for what is allowed to re-arm a cap at all.

Two things travel alongside it: `collectEvents()` gives up its implicit default timeout (a withdrawn bound, and the one thing here that can change an existing consumer's behaviour without them touching a line), and the model catalogue gains Opus 5.5, which drags the claude-code SDK dev-pin floor forward with it.

Nothing in this release is a required-config change. Both new fields are optional, and omitting either is specified as a guarantee rather than a default: no adapter arms a timer and no fallback value is substituted.

## New: a per-tool-call cap

`RuntimeExecuteParams` gains an optional field:

```ts
toolCallTimeoutMs?: number   // milliseconds; bounds ONE tool call
```

Semantics:

- **Armed** when a `tool_use` event is emitted; **disarmed** by the matching `tool_result`.
- **Armed per call, not per run.** Two sequential tool calls each get the full configured value; a series of short calls accumulates nothing.
- On expiry the **run** ends with `AdapterToolCallTimeoutError` in the `runtime` phase, naming the call it cut short.
- **Absent field = no timer at all.** No adapter arms a per-call timer and there is no fallback default; a hung tool call is then bounded only by `timeoutMs`, or by nothing.

**Expiry ends the run, not the call.** This is deliberate: nothing in the contract can hand the model a result for an abandoned call. The channels that point inward — `pushMessage()`, `onUserInput` answers, tool-approval decisions, declarative gating fields — all gate a call *before* dispatch; none of them interrupts one in flight. A per-call stop (end the call, synthesize a failed `tool_result`, let the turn continue) was considered and rejected because no adapter can honour it today: claude-code leaves `Query.stopTask()` unconsumed and treats `Query.interrupt()` as strictly fire-and-forget on the teardown path, and codex, opencode and gemini expose nothing of that shape. Coarse whole-run stop is the contract until all four SDKs can do better.

**Two exemptions — tool calls this cap does not apply to:**

1. A `tool_use` that **opens a subagent**. It is bounded by `subagentTimeoutMs` alone; the two caps never race on the same object.
2. A `tool_use` with an **unanswered `user_input_request` under it** (MCP elicitation, tool-approval prompt). A human is slow, not the call — so such a call is bounded by nothing but `timeoutMs` and `abort()`. The exemption lifts once the request is answered, and the cap then arms on the remainder of the call.

Two more boundary cases, both settled without special-casing:

- Engine-backgrounded shell work (claude-code's `run_in_background`) does not collide with the cap: the call that *starts* it settles immediately, and the running process is bounded by the background hold cap instead.
- A nested turn started from inside a tool call is, from this run's perspective, an ordinary tool call, and is capped flat.

## New: a per-subagent cap

```ts
subagentTimeoutMs?: number   // milliseconds; bounds ONE open subagent
```

It is a field of the **run**, not of the subagent definition envelope — a subagent the model spawns with no consumer definition behind it would otherwise carry no bound at all.

- **Armed** when a subagent opens.
- **Re-armed** — returned to its full value — by that subagent's own lifecycle events only: its `subagent_started` (including a re-entry's `resumed: true` start) and every `subagent_progress` carrying its `taskId`. Without the re-arm the cap would cut short a subagent that is visibly working, which is the failure it exists to prevent.
- **Nothing else on the stream re-arms it.** Movement at large does not count.
- **On expiry** the run ends, and the open subagent leaves through the same synthesized closure as any other termination (below).
- **Absent** = no subagent carries a cap; an open one is bounded by `timeoutMs`, the hold cap or `abort()` alone.
- Cross-adapter caveat carried in the spec: where subagent lifecycle is synthesized rather than native, the cap is worth exactly what the synthesis is worth. The per-adapter capability matrix says so up front rather than letting the guarantee quietly change meaning per architecture.

**The subagent-closure rule now lists four triggers instead of three.** A subagent still in flight when `abort()`, `timeoutMs`, hold-cap expiry **or `subagentTimeoutMs` expiry** terminates the run is closed by a synthesized:

```
subagent_completed { status: 'aborted' }
```

fired for every `subagent_started` still unpaired at teardown, **at most once per `taskId` per termination**. A subagent that already produced its own terminal event is not closed a second time. `idleTimeoutMs` is explicitly *not* on that list — it does not advance while a subagent is open and can never cut one short.

## What counts as "outstanding work" for the idle clock

`idleTimeoutMs` only fires when the run owes the consumer nothing. The enumeration of what counts as outstanding gains one member — **a `streamingInput` session whose input channel is still open, waiting for the next push**: a producer on the consumer's side being slow, rather than an engine gone quiet.

Each kind of outstanding work is now explicitly paired with the cap that bounds it:

| Outstanding work | Bounded by |
| --- | --- |
| tool call in flight | `toolCallTimeoutMs` |
| open subagent | `subagentTimeoutMs` |
| unsettled background task | the hold cap (`claude_backgroundHoldCapMs` on claude-code) |
| open streaming-input channel | the backstop `timeoutMs`, which spans the whole session |
| nested turn | the clocks of its own `execute()` call — a separate run with an independent clock set |
| unanswered `user_input_request` | **nothing** — the one item with no cap of its own |

Consequence for mid-turn input: across a `pushMessage` gap the backstop and the idle clock behave differently, and **only the backstop actually runs between pushes**. A push buys no fresh budget; one `timeoutMs` and one idle clock span the whole `execute()` call. But the idle clock does not advance while the channel sits open waiting, however long the consumer leaves it. What ends a streaming session is unchanged: the channel draining, `timeoutMs` firing, or `abort()`.

Consequence for human-in-the-loop: a run parked on an unanswered `user_input_request` can be ended by `abort()` and `timeoutMs` only — never by `idleTimeoutMs`, and now explicitly never by `toolCallTimeoutMs` either. An elicitation reaches the consumer from inside an open `tool_use`, so a cap on that call would cut a human short by a clock that never measured the human.

## The clock count goes from four to six — and re-arming gets a rule

The clocks a run can be subject to were: the backstop (`timeoutMs`), the idle clock (`idleTimeoutMs`), the hold's grace window, the hold's hard cap. They are now six, adding the tool-call cap and the subagent cap.

With more caps comes the constraint that keeps them honest: **what re-arms a cap is a closed vocabulary, not the stream at large.** Only the matching `tool_result` for *that* call, the lifecycle events of *that* one subagent, and the lifecycle events of *that* one background task re-arm anything. A bound may not rest on raw event cadence — no capability matrix anywhere records how densely an adapter speaks — only on a signal whose per-adapter behaviour some matrix already declares. The grace window is the sole exception: it bounds no work, so any frame legitimately re-arms it.

## The background hold cap now re-arms

Previously the cap was a single timer armed once, at the held `result`: "an absolute cap on the parked stretch". It is now a cap on **unsettled work**:

- **Re-armed** by every `background_task_started` / `background_task_progress` / `background_task_completed` belonging to a task the adapter tracks.
- **Expires** only after that many milliseconds in which no such event arrived *while something was still unsettled*.
- The transport frames `system/status` and `background_tasks_changed` do **not** re-arm the cap — they re-arm the **grace window** instead. On claude-code specifically, the cap is re-armed only by the `task_started` / `task_progress` / `task_notification` frames the adapter routes into a tracked task's `background_task_*` family, and by nothing else.
- Still released the moment a continuation turn begins; from there the run is an ordinary live turn bounded by `timeoutMs` / `abort()`.

This is not a heartbeat — it is not moved by arbitrary stream traffic. The practical difference: a backgrounded `sleep 3600` stays silent and is still cut at the cap, while a build emitting `background_task_progress` for twenty minutes is not cut, because it is visibly working. The old arm-once cap could not tell those two apart.

The two bounds are now stated as measuring different things: **grace** measures engine silence once everything tracked has settled; **cap** measures silence from a tracked task while something is still unsettled. Neither measures the length of the parked stretch — a task that keeps reporting progress extends it indefinitely and neither bound objects.

Their expiries differ in kind:

- **Grace expiry** is silent: it closes the channel and the run ends at `result` like any healthy task-touching run.
- **Cap expiry** is terminal `error`: it interrupts the session down the same path as `abort()`, and the run's last event carries `AdapterBackgroundHoldExpiredError`. The error is typed (distinguishable by class *and* by a `name` that survives serialization, so it is never confused with a consumer `abort()` or a `timeoutMs` expiry), carries the cap value as a field and in the human-readable message, and **names the `architectureConfig` key that raises it** (`claude_backgroundHoldCapMs`). It is terminal: any remaining background task is abandoned and its completion is never reported.

Unchanged but worth re-stating, because the re-arm rule leans on it: a `taskId` already marked finished that sees a second `task_started` re-enters the tracked set and re-arms **both** bounds.

claude-code's hold levers are unchanged in name and default: `claude_backgroundGraceMs`, `claude_backgroundHoldCapMs` (default **90s**), and `claude_disallowBackgroundBash: true` (default off — backgrounding stays available; setting it denies the backgrounding parameter so the command runs synchronously).

## `collectEvents()` no longer applies a default clock

This is the one behavioural withdrawal in the release, and the only change a consumer can feel without opting in.

```ts
collectEvents(stream)   // drains until the stream ends, however long that takes
```

There is **no default bound**. A consumer that wants one must pass one. The helper is consumer-side and is not one of the adapter-side clocks; omitting a bound is a guarantee, not a request for a guess. Concretely: a stream that keeps emitting without pause for many minutes returns every event of it, and nothing in the helper ends consumption on elapsed time.

Before 0.9.13 the spec described `collectEvents()` as carrying a **120-second default**, and the claude-code hold cap's 90s default was explicitly justified as sitting under it. That justification is gone: 90s is now framed as "the measured starting point", nothing more.

**Two consequences to act on:**

1. Any code, test or comment that assumed `collectEvents()` gives up after ~2 minutes is now spec-contradicted and will instead wait for the stream to end.
2. The sizing obligation moved from the library to the consumer. There is no library-side ceiling left for an adapter default to sit under, so **a consumer who applies a stream timeout must lower `claude_backgroundHoldCapMs` to match** — otherwise the cap can never surface its own typed error before the generic stream timeout fires first, because the cap only arms at a held `result`, later than a clock started at run start. The levers' documentation says to raise a stream timeout and the cap together, never either alone.

Related, and unchanged in intent but now stated: `takeUntilResult()` — and any helper that stops consumption on `result` — treats a `result` with a non-empty `backgroundTasks` as **not terminal** and keeps consuming. A helper that stopped at the first `result` regardless would reproduce exactly the bug the background-task hold exists to prevent.

## Error surface

The hierarchy gains one class and the package root gains two exports.

New class:

```
AdapterToolCallTimeoutError   // toolCallTimeoutMs exceeded — one tool call stood still
```

- Phase: `runtime`.
- Carries `toolName` and `toolUseId` of the call it cut short — without which the consumer is told that *a* tool hung and not *which*. Both survive `toJSON()`.
- Terminal: it stops the run down the same path `timeoutMs` uses.
- Distinguishable by `instanceof` and by `.name`, which survives serialization.

`AdapterIdleTimeoutError` must likewise be distinguishable from `AdapterTimeoutError` **by name after serialization**, not merely by `instanceof` in memory.

The three timeout errors are now framed as three different diagnoses:

| Error | What it says | What to look at |
| --- | --- | --- |
| `AdapterTimeoutError` | the run outlived the budget it was given | a number to raise |
| `AdapterIdleTimeoutError` | the run went quiet while owing the consumer something | an engine to look at |
| `AdapterToolCallTimeoutError` | one call stood still while the run around it was healthy | a tool or a server to look at |

Package-root exports, before → after:

```diff
- AdapterError, AdapterInitError, AdapterTimeoutError, AdapterAbortError,
- AdapterBackgroundHoldExpiredError, AdapterToolPolicyError
+ AdapterError, AdapterInitError, AdapterTimeoutError, AdapterIdleTimeoutError,
+ AdapterToolCallTimeoutError, AdapterAbortError, AdapterBackgroundHoldExpiredError,
+ AdapterToolPolicyError
```

`AdapterToolCallTimeoutError` is genuinely new. `AdapterIdleTimeoutError` already existed in the hierarchy but was absent from the export list — verify the actual package entry point, because if consumers could not import it from the root before, that is a packaging gap being closed rather than a new surface. Counts move accordingly: seven non-base classes instead of six, and "five of six end a live run" (excluding init and tool-policy).

## Opus 5.5

New model across two architectures:

| Architecture | Alias | Resolved id | Context window |
| --- | --- | --- | --- |
| claude-code | `opus-5.5` | `claude-opus-5-5` | 1,000,000 |
| opencode-openrouter | `claude-opus-5.5` | `anthropic/claude-opus-5.5` | 1,000,000 |

So `resolveModel('claude-code', 'opus-5.5')` returns `'claude-opus-5-5'`.

`ADAPTIVE_THINKING_ONLY` gains `claude-opus-5-5`. The set is keyed by **resolved Anthropic model id** and its full membership is now:

```
claude-fable-5-1, claude-fable-5, claude-sonnet-5,
claude-opus-4-6, claude-opus-4-7, claude-opus-4-8,
claude-opus-5, claude-opus-5-5
```

It holds **bare Anthropic ids only** — the OpenRouter form `anthropic/claude-opus-5.5` is deliberately excluded, because the class is meaningful only for architectures whose resolved ids are bare Anthropic strings.

Opus 5.5 joins that class in a stronger sense than its predecessors: its adaptive thinking is **always on and cannot be disabled at any reasoning effort**, so membership is a constraint the model enforces rather than merely the absence of a fixed-budget mode. `thinking: { type: 'disabled' }` is a 400 at *every* effort level, not only at `xhigh`/`max` as on plain Opus 5. The adapter never emits `'disabled'`, so this is unreachable today — but it forecloses a future disabled-thinking path entirely rather than partially.

**Silent-regression warning for consumers:** Opus 5.5's default reasoning effort is **`medium`**, while every other model — Opus 5 included — defaults to `high`. The ladder itself is unchanged (`low | medium | high | xhigh | max`). A consumer who omits `claude_effort` and simply switches the model id to `claude-opus-5-5` runs one effort level lower than before, with nothing in the API to signal it.

**SDK floor moves.** The supported peer range is unchanged at `@anthropic-ai/claude-agent-sdk >=0.3.0 <0.4.0`, but the recommended dev-pin floor goes from `^0.3.251` (resolved `0.3.263`) to `^0.3.280` (resolved `0.3.280`), because `claude-opus-5-5` requires CLI ≥ 2.1.280. On the old pin the failure arrives as a normal runtime result with `is_error: true` *after* a clean `system:init` — never as an init fault:

```
API Error: 400 Claude Code 2.1.263 does not support this model;
version 2.1.280 or newer is required. Run 'claude update',
or update the Claude desktop app, then try again.
```

Any CI or environment pinned below `0.3.280` will get exactly that the moment Opus 5.5 is requested.

Verification on the new pin is **partial**: only a targeted `opus-5.5` probe and leg 1 of the SDK surface probe were run. Legs 2 and 3 and the full `test:e2e:claude:*` suite remain pending. Leg 1's finding: an unrestricted run's `system:init` at `0.3.280` advertises 25 built-ins — `Task, Bash, CronCreate, CronDelete, CronList, DesignSync, Edit, EnterWorktree, ExitWorktree, ListAgents, Monitor, NotebookEdit, PushNotification, Read, RemoteTrigger, ReportFindings, ScheduleWakeup, SendMessage, Skill, TaskStop, ToolSearch, WebFetch, WebSearch, Workflow, Write` — all 25 known to the tool-gating inventory, zero unknown names. This measures the *advertised* list of one live run, not the published tool-input-schema set of 45 names, so it does **not** retire the earlier "29 catalogued tools stripped under any deny" gap finding.

## How this release is classified

Everything additive here — two optional `RuntimeExecuteParams` fields, one new error class, one more entry on the outstanding-work list, a hold cap that now re-arms — is a **minor**: nothing is renamed, nothing is removed, and a consumer setting neither field sees exactly the run it saw before.

The exception is `collectEvents()` losing its default clock. The signature does not move and the surface is not even opt-in, yet a consumer who relied on the helper giving up after about two minutes now waits for the stream to end. That is a bound *withdrawn* rather than tightened, and it carries the same obligation: minor, **with a changelog note naming the withdrawn default and the argument to pass in its place**.

The release also settles a versioning rule that had been argued case by case: **a surface that keeps its name and its type while its meaning changes is a major.** Nothing is removed and no signature moves, so it reads as additive, while every consumer already calling it is now asking for something other than what it asked for before — and no compiler catches that.

## For implementers

Ordered roughly by dependency: types first, then the machinery that reads them.

1. **Types — `RuntimeExecuteParams`** (unified core, L1). Add two optional fields:
   ```ts
   toolCallTimeoutMs?: number
   subagentTimeoutMs?: number
   ```
   Both on the run params, not on any subagent-definition envelope. Do not give either a default value anywhere in the type or in adapter normalization — absence must stay observable.

2. **Error classes and package-root exports** (errors & resilience, L4). Add:
   ```ts
   class AdapterToolCallTimeoutError extends AdapterError {
     readonly phase = 'runtime'
     readonly toolName: string
     readonly toolUseId: string
   }
   ```
   Include `toolName` and `toolUseId` in its `toJSON()`. Verify `name` survives serialization for both this class and `AdapterIdleTimeoutError`. Then export from the package root, in this order:
   `AdapterError, AdapterInitError, AdapterTimeoutError, AdapterIdleTimeoutError, AdapterToolCallTimeoutError, AdapterAbortError, AdapterBackgroundHoldExpiredError, AdapterToolPolicyError`.
   Check whether `AdapterIdleTimeoutError` was actually reachable from the entry point before this release — if not, note the fix separately from the new class.

3. **Tool-call cap machinery**, in whatever shared run-supervision layer each adapter routes its unified event stream through. Arm a timer on each emitted `tool_use`, key it by `toolUseId`, clear it on the matching `tool_result`. On fire, terminate the run with `AdapterToolCallTimeoutError` carrying that call's `toolName` and `toolUseId`. Implement the two exemptions at arm time and at answer time: never arm for a `tool_use` that opens a subagent; suspend while an unanswered `user_input_request` sits under the call, and arm on the remainder when it is answered. Confirm the timer is per-call: two sequential calls each get the full value.

4. **Subagent cap** (subagents module). Arm when a subagent opens; re-arm to full on that subagent's own `subagent_started` (including re-entry starts carrying `resumed: true`) and on every `subagent_progress` whose `taskId` matches. Do not re-arm on anything else. On expiry, terminate the run through the existing teardown path so the synthesized-closure sweep runs: emit `subagent_completed { status: 'aborted' }` for every unpaired `subagent_started`, at most once per `taskId` per termination, skipping any subagent that already produced a terminal event. Make sure `idleTimeoutMs` does not advance while a subagent is open.

5. **Idle-clock outstanding-work predicate**. Add "streaming-input channel open and waiting for a push" to whatever function decides the run owes the consumer something. Leave the backstop running across that gap — only the idle clock is suspended.

6. **Background hold cap re-arming** (background tasks / claude-code adapter). Replace the arm-once timer with one re-armed by tracked-task lifecycle events. In the claude-code adapter, that means the `task_started` / `task_progress` / `task_notification` frames the adapter routes into a tracked task's `background_task_*` family — and explicitly *not* `system/status` or `system/background_tasks_changed`, which must keep re-arming the grace window only. Keep `claude_backgroundHoldCapMs` default at 90s, but remove any comment or constant deriving it from a `collectEvents()` default. Ensure `AdapterBackgroundHoldExpiredError` carries the cap value as a field, in its message, and names `claude_backgroundHoldCapMs` as the key that raises it.

7. **`collectEvents()`** (stream consumption). Remove the implicit default timeout. The helper drains until the stream ends unless the caller passes a bound. Audit tests and fixtures for any reliance on the old ~120s give-up. While in that file, confirm `takeUntilResult()` treats a `result` with a non-empty `backgroundTasks` as non-terminal and keeps consuming.

8. **Model catalogue** (models & aliases). Add alias `opus-5.5` → `claude-opus-5-5` (1M window) for claude-code and `claude-opus-5.5` → `anthropic/claude-opus-5.5` (1M window) for opencode-openrouter. Add `claude-opus-5-5` to `ADAPTIVE_THINKING_ONLY`; do **not** add the OpenRouter form — the set holds bare Anthropic ids only. Set the default reasoning effort for `claude-opus-5-5` to `medium`.

9. **SDK pin and verification** (claude-code adapter, L7). Bump the dev pin from `^0.3.251` to `^0.3.280`; leave the peer range at `>=0.3.0 <0.4.0`. Then run the still-pending verification on that pin: legs 2 and 3 of the SDK surface probe and the full `test:e2e:claude:*` suite.

10. **Changelog.** One entry is mandatory rather than optional: `collectEvents()` no longer applies a default timeout — name the withdrawn ~120s default and the explicit argument callers should pass instead. Worth adding alongside it: consumers moving to `claude-opus-5-5` without setting `claude_effort` silently drop from `high` to `medium`.
